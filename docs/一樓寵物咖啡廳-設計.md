## 一、定位：它是什麼、不是什麼

**是**：房東經營的延伸。你在三樓觀察租客的生活，在一樓看見這棟樓與外界的接觸面。
咖啡廳是**故事的入口**，不是一個獨立的經營遊戲。

**不是**：時間管理遊戲。沒有點單小遊戲、沒有拉霸、沒有體力值。
玩家不會被要求「每天上線點五十下」。

核心體驗的一句話：

> 你養的貓在樓下曬太陽，一個客人蹲下來摸牠，然後問你：這孩子可以認養嗎？

咖啡廳的**經濟迴圈是骨架，敘事接縫是血肉**。若某個設計決定同時服務兩者，優先做；只服務經濟的，往後排。

## 二、已拍板的四個決定（2026-08-01，使用者）

| 決定 | 選擇 | 影響 |
|---|---|---|
| 呈現方式 | **畫進樓層地圖** | 底層共用 grid 與 viewport（見 §3.2），但玩家看到的是獨立樓層頁面 |
| 經營節奏 | **常備訂單 ＋ 研發決策** | 進貨自動跑、離線不斷貨；玩家的真決策集中在低頻高重量的選擇 |
| 樓層編號 | **租客維持三樓** | 1F 咖啡廳、2F 不進遊戲、3F `r301`~`r304`。**存檔零遷移** |
| 樓層導覽 | **兩個獨立頁面＋單一目的地按鈕** | 3F 只有「前往 1F」，1F 只有「返回 3F」；不用同頁雙 tab，不呈現成連續畫布 |

第三點的理由值得記：`roomId` 是 `state.occupancy`、`placements[].room`、`upgradeState.byRoom` 的 key，全都進存檔。改名等於升 `SAVE_VERSION` 並替所有玩家的舊檔寫遷移，換來的只是一個數字更好聽。不值得。

敘事上把 2F 設定成「屋主自住／長期空置」，未來若要擴充是現成的坑位。

## 三、樓層架構

### 3.1 地圖擴充

現況：`TILE=16`、`GRID_W=16`、`GRID_H=33`（`src/floor/map.ts:17-19`），畫布固定 256×384。
`Region`（`map.ts:21-32`）是扁平 11 成員 union，**沒有樓層維度**；座標是單一 `(c,r)`。

**方案：往下延伸同一張 grid，不引入 `floorId`。**

```
rows  0–32   3F  現有樓層（一格都不動）
row   33     樓板分隔帶（wall region）
rows 34–51   1F  咖啡廳
```

`GRID_H` 33 → **52**。

這個選擇的關鍵洞見：**「多一層樓」在 2D 俯視格子裡不需要新維度，一道牆加一段樓梯就夠了。**
尋路（`pathfind.ts:49` 單一 grid BFS）、agents、petAgents、groupScene **全部自動生效**，租客可以真的走下樓。
代價只在畫面，而畫面問題有現成解（§3.2）。

⚠️ **rows 0–32 必須逐格不動。** 這是零漂移的第一道防線——現有租客的作息、尋路、家具目標完全不受影響。

### 3.2 Viewport 與樓層頁面：玩家分頁，程式共圖

勘查說「專案沒有任何鏡頭機制，必須做一個全新的」。**這句話不完全對。**

`src/components/PixelDollhouse.vue:122` 的房間特寫**已經在用 `composeFloor` 加 scale+translate 畫相機窗格**（見 `scripts/roomcam-test.ts` 檔頭）。也就是說「只畫地圖的一部分並放大」這件事，專案裡有**已上線、有測試覆蓋**的實作。

所以樓層鏡頭的做法是：把 `PixelDollhouse` 的窗格邏輯抽成共用的 `FloorViewport`，讓它接受一個矩形（而非房間），`FloorMap.vue` 的兩個樓層頁面各自使用一個固定機位：

```
3F 視角  rect = (0, 0, 16, 33)
1F 視角  rect = (0, 34, 16, 18)
```

UI 不把它畫成同一頁上的「3F／1F」雙 tab，也不讓玩家捲過樓板看到另一層；**玩家看到的是兩個獨立樓層頁面**：

```
🏠 3F 租屋樓頁面       [☕ 前往 1F 寵物咖啡廳]
              ⇅ 單一按鈕整頁切換
☕ 1F 寵物咖啡廳頁面   [🏠 返回 3F 租屋樓]
```

每個頁面只出現一個明確目的地按鈕，切換時替換整個樓層畫面；之後也能各自承載租屋操作與咖啡廳管理，不必把兩套功能塞進同一個 tab 列。**不做自由捲動、不做縮放手勢**——兩個固定機位就夠，而且手機上更好用。

底層仍共用同一張 52-row grid、同一套 agents 與尋路。這是實作細節，用來保留租客真的能走樓梯下樓的能力；**不代表玩家介面要呈現成一張上下連續的地圖**。

這把最大的成本項從「全新子系統」降級成「重構一個已驗證的元件」。

### 3.3 樓梯

`Region` 新增 `stairs`。位置在 `col 7-8`（沿用現有走廊的縱向軸線，`LOUNGE_HALL_RECT` 就在 `{7,1}→{8,31}`），跨越 row 32–35。

租客下樓 = 一段正常的尋路。玩家在 1F 視角會看到有人從樓梯口走進來。
**不需要傳送、不需要跨樓層尋路特例。**

⚠️ **三處硬編白名單必須同步**（漏改會靜默出錯）：
`placements.ts:140` `FLOOR_REGIONS`、`routine.ts:166` `COMMUNAL`、`comfort.ts:308` `COMMUNAL_AREA_IDS`。

🔴 **`COMMUNAL_AREA_IDS` 是唯一「必須不加」的那個。**

設計上的正當理由：**咖啡廳是營業空間，不是住戶共用設施**。租客的居住舒適度不該因為樓下開店而改變。

## 五、核心迴圈

### 5.1 一句話

> 房租進來 → 投資設備與研發 → 客流與客單價上升 → 咖啡廳收入 → 再投資
> 而客流本身會帶來**租屋詢問**與**認養詢問**，回頭餵養主線。

**關鍵設計原則：咖啡廳不該比收租賺錢。**
它的產出是**故事與人流**，錢只是讓迴圈能自轉。若咖啡廳變成最優收益手段，整個遊戲的重心就跑掉了。
數值目標：成熟期咖啡廳日淨利 ≈ 日租金收入的 **30–50%**。

### 5.2 常備訂單（自動，不懲罰離線）

玩家設定每種原料的**常備量**，系統每日自動補到該水位並扣款。

```
原料        常備量    單價    今日消耗
咖啡豆       [20]     $15      12
牛奶         [15]     $12       9
麵粉         [10]     $8        4
貓罐頭       [ 8]     $25       3
```

- 錢不夠 → 只補得起多少補多少，並推一則日誌（不是懲罰，是敘事）
- 常備量設太低 → 熱門品項賣完，當日客流打折 + 一則「客人撲空」日誌
- 常備量設太高 → 生鮮類會過期損耗（只有生鮮，乾貨不會）

**玩家可以設一次就三個月不管。** 這是刻意的——它讓「偷懶」變成一個有代價但可接受的選擇，而不是失敗狀態。

### 5.3 研發（低頻、高重量、日數倒數）

不發明新機制，**照抄既有的日數倒數**（`wishes.ts`、`floorChain.ts`、`pets.ts:133` 的 `rehomingAtMs`）。

```
研發中：貓掌棉花糖拿鐵
剩餘 3 天 ・ 已投入 $4,000
完成後：客單價 +8%，吸引「甜食客」客群
```

- 同時只能研發一項（決策有重量）
- 每項有前置需求（設備或先前的研發）
- 研發完成 → 菜單多一項 → 影響客流結構而非單純加數字

**研發樹草案（第一期只做前兩層）：**

```
基礎沖煮 ──┬── 手沖單品 ──── 季節限定豆
           ├── 拿鐵拉花 ──── 造型拿鐵（貓掌）
           └── 冷萃

烘焙 ──────┬── 司康 ──────── 下午茶套餐
           └── 貓咪造型餅乾

寵物餐點 ──┬── 寵物友善點心
           └── 寵物生日蛋糕 ★ 觸發特殊事件
```

★ 標記的項目會解鎖敘事事件，不只是數值。

### 5.4 投資（一次性、永久、不可退）

開張費定為 **$12,000**。種子局起始資金 $52,000 付完後，仍能同時買下點餐吧台 $16,000 與
商用濃縮咖啡機 $18,000，留下 $6,000 周轉；配合剛開張平均日淨利為正，不會形成付了錢卻無法營業的陷阱。

語意與既有的 `buyUpgrade()`（`economy.ts:358`）完全同構：一次性、不可退、永久生效。CAFE-14
維持 `cafe.ts` 的純函式邊界，`openCafe()`／`buyCafeUpgrade()` 回傳下一份 `CafeState`、精確成本、
交易後餘額、label 與 `category: "cafe"`；失敗則回傳原 state 與原餘額。CAFE-15 面板收到成功結果後，
才透過既有金流入口扣款、套用 state 並存檔，避免算式層直接依賴全域 state／economy。

| 投資項 | 價格 | 效果 |
|---|---|---|
| 第二台咖啡機 | $18,000 | 尖峰時段不再流失客人 |
| 貓跳台與軟墊 | $12,000 | 寵物停留時間 ↑ → 認養詢問頻率 ↑ |
| 戶外座位 | $25,000 | 晴天客流 ↑，雨天無效 |
| 大型冷藏 | $15,000 | 生鮮損耗 ↓ |
| 店面招牌 | $30,000 | 基礎客流 ↑，且**提高租屋詢問頻率** |

#### 5.4.1 營運面板（CAFE-15）

玩家從樓層頁下方的「☕ 咖啡廳」按鈕開啟獨立 bottom sheet；它是營運工具，不取代 3F／1F 的
樓層切換按鈕。未開張時只顯示 $12,000 開張成本、目前資金與確認按鈕，且不會暗自建立常備訂單。
開張後同一面板依序提供：最近單數／人氣／淨利、產能與缺貨預估、六種原料的常備量草稿、五項
永久投資，以及認養詢問的接受／婉拒決策。

- 常備量先改本地草稿，只有按「套用常備量」才寫入 `state.cafe.standingOrders` 並存檔；
  「恢復建議」也只重設草稿，避免開面板就改變遊戲狀態。
- 開張與投資成功後，面板才套用純交易結果，再透過 `addMoney(..., category: "cafe")` 留下收支流水並存檔；
  失敗不扣款、不套用結果。
- 接受認養先呼叫 `acceptCafeGuestAdoption()`；只有成功後才移除該詢問顧客。婉拒只移除詢問，寵物不變。
- CAFE-15 已把決策 UI 與命令接好；CAFE-22 也已讓永久樓寵物真正走進 `cafe_pet`，公開最低範圍
  因此具備玩家可達的認養流程（目前仍不是以 ephemeral agent 座標作為硬性資格，見 §7.3）。

### 5.5 客流模型

**公式形狀直接抄 `coinLaundryIncome()`（`economy.ts:27`）**——「設備數 × 係數 × 條件數」，已在正式版跑了很久。

```
基礎客流 = 招牌等級 × 天氣係數 × 星期係數
實際客流 = min(基礎客流, 產能上限)         ← 產能來自設備投資
營收     = 實際客流 × 客單價
客單價   = 基礎價 × (1 + Σ 研發加成)
淨利     = 營收 − 原料成本 − 固定成本
```

天氣走既有的 `weatherForDay()`（`weather.ts:21`，splitmix32、零 RNG）。
星期走既有的 `week.ts`。**兩者都是現成的確定性來源。**

## 六、顧客：這個設計最難的部分

### 6.1 為什麼難

這遊戲裡**每一個看得見的人都綁死在 `TenantRuntime`**，而 `state.runtimes` 被 `tick`、`socialPass`、`collectRent`、`petsPass`、`diaryPass`⋯⋯十幾個 pass 用 `Object.values` 迭代。
放一個假 runtime 進去會污染收租、社交、日記、成就、週報**全部**。

這正是 🔴「訪客 NPC」卡住的真正原因。**做咖啡廳等於順手解掉它。**

### 6.2 解法：`CafeGuest` — 一個平行的、不進 `state.runtimes` 的輕量體

資料形狀抄 `GroupSceneActor`（`groupScene.ts:20`，已證明「一組顏色快照就能畫出一個沒有 runtime 的人」）：

```ts
interface CafeGuest {
  id: string;
  name: string;              // 獨立姓名池，不與租客共用
  appearance: Appearance;    // 既有外觀池 × 顧客 seed 的決定性選取（零 RNG）
  intent: "coffee" | "adopt" | "rent";
  arrivedMs: number;
  leavesMs: number;          // 停留 1~3 遊戲小時
  seatTile: Tile | null;
}
```

存在 `state.cafe.guests: CafeGuest[]`，**cap 6**。

- 不進 `state.runtimes` → 十幾個 pass 完全不受影響
- 不進 `relationships`、不進 `state.occupancy`、不收租、不寫日記
- `GuestAgent` 只保存顯示期狀態，生命週期為 `entering → seated → leaving → departed`；從
  `cafe_entrance` 進場，找可達且未被家具阻擋的座位，停留後再走回入口
- 渲染沿用 `floorScene` 的人物 sprite 與 y-sort，但走獨立 `drawGuest()` 分支，不依賴
  `TenantRuntime` 或租客 registry
- 到 `leavesMs` 時只切換為離場走位；抵達 `cafe_entrance` 後才從 `state.cafe.guests` 移除，
  **不會原地消失，也不留任何殘留**

CAFE-08 先提供純 `GuestAgent` 與 `composeFloor(..., guests)`／離線 renderer 驗證。正式頁面的
`state.cafe.guests` 來源要等 CAFE-11 建立 schema、CAFE-13 接客流後才啟用；在咖啡廳尚未開張時，
1F 畫面維持沒有假顧客。

⚠️ **獨立姓名池**：`NAME_IDENTITIES`（`recruit.ts:193`）只有 20 筆且與租客共用（靠 `excludeNames` 排除在住者）。顧客共用會撞名。

### 6.3 三種意圖

| intent | 頻率 | 接到哪個既有系統 |
|---|---|---|
| `coffee` | 最高 | 無，純客流與氛圍 |
| `adopt` | 中 | **`beginRehoming`/`finishRehoming`（`pets.ts:124/141`）** |
| `rent` | 低 | **`state.applicantPools`（`recruit.ts`）** |

三種意圖都以顧客頭上的 16×16 思考泡泡呈現：咖啡杯、愛心與租屋信封。每種從 LimeZu thinking
emote sheet 取兩幀，`FloorMap` 每 500ms 推進一次 frame，因此以偶／奇幀切換形成約 1 秒循環。
泡泡只在顧客已入座且停止移動時出現，繪製在人物與家具 y-sort 之後的資訊層；進場、離場、移動中
或 hidden 顧客不顯示。`cafe.png` 未載入或 Canvas `drawImage` 失敗時，改畫可辨識的程序咖啡杯／
愛心／信封 fallback，不修改共用人物 sprite 或 `src/pixel/*`。

CAFE-10 只完成渲染能力與離線三意圖驗證。正式頁面仍遵守 CAFE-08 的資料閘門：CAFE-11 建立
`state.cafe`、CAFE-13 產生客流前，未開張的 1F 不建立假顧客，也不顯示示範泡泡。

## 七、三條接縫（這是整個設計的價值所在）

### 7.1 顧客問認養 → 寵物送養

**接得最乾淨的一條**，因為 Codex 剛做完 `0b40d42`。

- 條件：`cafe_pet` 區有樓寵物（`ownerId === "landlord"`）在場，且該寵物未在送養流程中
- 顧客頭上冒出思考泡泡 → 玩家可點擊 → 抉擇面板
- 同意 → `acceptCafeGuestAdoption()` 驗證 `intent === "adopt"`、永久樓寵物與未在媒合中，
  再直接重用既有 `finishRehoming`；新產生的名冊項目把 `destination` 改寫成
  「咖啡廳客人領養」（`PetHomeEntry.destination` 是**自由字串**，不擴張送養中的 enum／存檔 schema）
- 同一顧客使用穩定 `cafe:<guestId>` 名冊 id；重複點擊不能領走第二隻，房客寵物、已在媒合中的
  樓寵物與非 `adopt` 顧客一律零變更拒絕
- 拒絕 → 寵物留下，推一則日誌

**回報極直觀**：幸福新家名冊立刻多一筆，玩家看得到自己養大的貓找到了家。

CAFE-09 只提供上述 sim 命令，不偽造顧客或寵物的現場位置。接受／婉拒 UI 已由 CAFE-15 接線，
CAFE-22 也已讓樓寵物能真正到達 `cafe_pet`；嚴格的「必須已在場」資格限制仍需另建共享位置狀態。

### 7.2 顧客問租屋 → 招租

- 條件：有空房
- 同意 → 生成一個 `Applicant` 放進 `state.applicantPools[roomId]`
- 這條顧客**看過咖啡廳**，所以帶一個小加成：初始好感 +5，或星等 +0.5

設計價值：**它讓「經營咖啡廳」變成「吸引好租客」的手段**，兩條主線終於互相餵養。
需要三樣東西（勘查已確認）：獨立姓名池、房間歸屬處理（用 `rescoreApplicants` 重算）、沿用該位
`CafeGuest.appearance`（不重新抽外觀、不新增 RNG）。

### 7.3 租客與寵物下樓

**租客**：走 `away` 的一種目的地（`outing.ts` 已證明零 RNG、零日誌筆數變化、零漂移）。
但因為咖啡廳這次**畫在地圖上**，不能沿用 `away` 的「不渲染」語意——需要一個新的 visualState `at_cafe`，讓人真的走下去坐著。

⚠️ 這是本設計**唯一必須新增 visualState** 的地方，也是最可能造成漂移的點。
緩解：設 `CAFE_FIRST_DAY` 閘門（比照 `outing.ts:55` 的 `OUTING_FIRST_DAY = 14`），讓 10 日快照窗內不可能觸發。

**寵物**：`petAgents.ts` 的走位範圍加上 `cafe_pet` 區。CAFE-22 只在渲染層改變有效目的地，
不改寫 `Pet.hangout`：咖啡廳已開張、10:00～15:59 的既有白天時段、`ownerId === "landlord"`、
永久安置且沒有進行中配對演出的樓寵物，會以 `petId + 當地日期小時` 的穩定雜湊得到 35% 下樓機率。
同寵物同小時結果固定，不新增 RNG，也不擾動串門、搗蛋、配對或日誌位置；命中後使用既有 BFS
從三樓走到 `cafe_pet` 的可走格。

目前 CAFE-15 面板與 CAFE-09 命令的認養資格仍是「所有永久樓寵物」，沒有把 ephemeral agent 座標
寫回 sim state，因此 CAFE-22 完成的是**畫面可達與跨樓層演出**，不是嚴格的「此刻已抵達寵物區才可認養」
伺服端規則。若日後要強制現場相遇，必須另設明確的共享位置狀態，不能拿 `hangout` 冒充。

**同框演出**：直接用 Codex 的 `startGroupScene`（`groupScene.ts:91`），新增一個 venue `"cafe"`。

## 八、存檔

`SAVE_VERSION = 6`（`persistence.ts:28`）。
**Additive 慣例白紙黑字寫在 `persistence.ts:242-245`**：「選填欄位，舊檔沒有就從空的開始，不需要升 SAVE_VERSION」。

整個咖啡廳是 **1 個 top-level key**：

```ts
state.cafe = {
  open: false,              // 玩家花錢開張才 true
  standingOrders: {},       // Record<ingredientId, number>
  stock: {},                // Record<ingredientId, number>
  research: null,           // { id, startedDay, days, invested } | null
  completed: [],            // string[]
  upgrades: [],             // string[]
  guests: [],               // CafeGuest[]
  popularity: 0,
  history: [],              // 日結紀錄，cap 60
};
```

**不需要升版。** 載入端 `s.cafe ?? defaultCafe()`。

⚠️ 咖啡廳設備存在 `state.cafe.upgrades`，**不是 `placements`**——否則玩家可以把咖啡機搬到三樓（`canPlaceFree` 只檢查 `FLOOR_REGIONS`）。
但**裝飾性家具**（桌椅、盆栽）可以進 `placements`，因為擺放是樂趣。兩者分開處理。

## 九、零漂移策略

`src/sim/outing.ts:6-40` 的檔頭是整個 codebase 最有價值的一段文件，逐條寫明如何加新子系統而不動快照。五條規則全部適用：

1. **10 日窗內零新增 `Math.random()`** — 內容選擇一律用確定性雜湊
2. **用遊戲日序號設閘門** — 但咖啡廳有更好的天然閘門：**它要玩家花錢開張**，無頭快照跑不會有人買 → 零漂移，連閘門都不用設
3. **窗內零新增 `addMoney`** — `money` 與 `ledgerCount`（精確整數 40）都在快照裡
4. **窗內零新增 `memoryTags`** — `memories` 是 3/2，未觸頂
5. **迭代次序固定** — 一律先依 id 排序

**三個必須避開的陷阱：**

| 陷阱 | 後果 | 解法 |
|---|---|---|
| 咖啡廳列進 `COMMUNAL_AREA_IDS` | `COMMUNAL_NEUTRAL` 失效，全盤漂移 | **不列**（§3.4） |
| 家具 insert 進 `INITIAL_PLACEMENTS` 中段 | `resolveTarget` 取陣列第一個符合的，全樓租客目標靜默改道 | **只 append，永不 insert** |
| `at_cafe` visualState 在窗內觸發 | 作息改變 → RNG 序列位移 | `CAFE_FIRST_DAY` 閘門 |

**驗證方法**：把每個 hook 拆成獨立可關閉的開關，一次只打開一個並各跑一次 `balance-test`，逐條記錄「哪個 hook 造成哪幾個欄位動了多少」。這比一次全開然後解釋一整面紅字容易十倍。

## 十、分期實作計畫

每一期都是可獨立驗收、可獨立上線的。

### 第 0 期：Viewport（前置，無遊戲內容）
把 `PixelDollhouse.vue:122` 的窗格邏輯抽成共用 `FloorViewport`，改成接受任意矩形。
`FloorMap.vue` 建立 3F／1F 兩個獨立樓層頁面，以單一目的地按鈕來回切換。**此時 1F 還是空的**，只驗證鏡頭與頁面切換本身。
驗收：`roomcam-test.ts` 全綠、三種手機寬度 `ui:shot` 無破圖。

### 第 1 期：地圖與空間
`GRID_H` 33→52、新增 6 個 Region、樓梯、樓板分隔帶、地板 tint、LimeZu 咖啡廳 atlas。
1F 有空間、有家具、**但沒有人也沒有經濟**。
驗收：`balance-test` 零漂移（rows 0–32 一格未動）、尋路可從 3F 走到 1F。

### 第 2 期：顧客與認養（MVP 的核心）
`CafeGuest` 型別、獨立姓名池、顧客進出與走位、**只做 `adopt` 一種意圖**，並完成
`CAFE-22` 讓樓寵物實際進入 `cafe_pet`。沒有寵物可接觸時認養意圖不可達，不能只靠測試直接呼叫函式假裝完成。
接 `beginRehoming`/`finishRehoming`。
驗收：幸福新家名冊會多出「咖啡廳客人領養」的紀錄；`state.runtimes` 零污染。

### 第 3 期：經濟迴圈
`state.cafe`、常備訂單、日結 pass（掛在 `collectRent()` 正後方）、客流公式、投資項。
投資層必須提供一次性的 `openCafe()` 開張動作；面板必須有開張按鈕、認養詢問的接受／婉拒操作、
常備量與投資操作，不能只顯示統計數字。
驗收：咖啡廳日淨利 ≈ 日租金的 30–50%；`balance-test` 零漂移（未開張）。

**公開上線建議**：做到第 3 期結束（CAFE-01～15 + CAFE-22），再由 CAFE-00 逐項關閉／開啟
每個模擬 hook 驗證零漂移，並完成手機三尺寸、舊存檔、開張→補貨→日結→投資、顧客認養的端到端驗收。
第 1 期只適合內部預覽：空間和家具已成立，但沒有顧客、認養或營運閉環，公開會像半成品。

### 第 4 期：研發
研發樹前兩層、日數倒數、菜單與客單價。

### 第 5 期：租屋詢問與同框演出
`rent` 意圖接招租、租客 `at_cafe` 下樓、`groupScene` 的 `cafe` venue。

**若要砍**：第 4、5 期可以無限期延後；`CAFE-22` 不在可砍範圍，前三期加上寵物可達性才是完整體驗。
