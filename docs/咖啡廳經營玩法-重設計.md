## 一、為什麼要重設計：現況診斷

使用者實玩後的原話是「**他們有點餐嗎 他們有消費嗎 什麼都不知道**」。
追進程式碼後確認，這不是玩家沒看懂，而是**系統真的沒有把這件事做出來**：

| 現況 | 事實 |
|---|---|
| 畫面上的顧客 | 營業時段每小時用固定門檻 `CAFE_ARRIVAL_CHANCE = 55` 決定生不生，**純裝飾** |
| 你賺的錢 | 換日時由 `cafeCrowd(天氣 × 星期 × 招牌 × 產能 × 人氣 × 戶外座位 × 氛圍)` 一次算出 |
| 兩者的關係 | **完全獨立。看到 2 個人或 6 個人，跟今天賺多少一毛錢關係都沒有** |
| 菜單品項 | `CafeMenuItem` 結構已存在，但只被拿去算「平均客單價」，**沒有任何顧客點過任何一項** |
| 原料 | 只有 `perGuest` 平均消耗量，跟品項無關；補貨是「設一次常備量就三個月不用管」 |
| 顧客座位 | 有 6 格 `CAFE_GUEST_PREFERRED_SEATS`，但開張贈品**刻意避開**這六格 ⇒ 顧客站在空地板上 |
| 虧錢 | 幾乎不可能。滿客 26 人時淨利約 +$156/日；缺貨只讓人氣 −4，不直接損失 |

**核心問題**：咖啡廳是一台「換日時吐出一個數字」的黑箱，而畫面上的人是螢幕保護程式。

## 二、設計目標（對應使用者的四點要求）

1. **有經營的感覺** — 玩家要看著「哪些產品賣得好」決定補什麼料；**顧客買不到會不高興，不只賺不到錢，還會掉聲譽**
2. **每天開店關店，營業期間畫面上真的看到人點餐、消費**
3. **要有可能虧錢**
4. **咖啡廳座位可以固定**（使用者主動放寬，換取實作單純）

## 三、核心轉變

```
現在：  換日 → 一條公式 → 一個營收數字
        （畫面上的顧客與此無關）

改成：  每個營業小時 → 幾位顧客進場 → 各自點一項商品
                                    ├─ 有料 → 收錢、坐下、喝完離開
                                    └─ 沒料 → 不高興、$0、聲譽 −、轉頭就走
        當日營收 = Σ 每位顧客實際點到的商品售價
```

**畫面上發生的事，就是帳本上發生的事。** 這是整個重設計的唯一主張，其餘都是它的推論。

### 為什麼架構上做得到（關鍵技術前提）

`syncToNow()`（`tick.ts:944`）是**逐小時**補進度的 —— 離線 8 小時就跑 8 次 `hourlyTick()`。
所以「每小時結帳」**天生支援離線**，不需要另外寫一套批次對帳，也不會有「線上結果 ≠ 離線結果」的分歧。
這是本設計成立的前提，也是它比「即時逐秒模擬」務實的地方。

## 四、系統設計

### 4.1 菜單品項：從裝飾變成真的商品

`CafeMenuItem`（`cafe.ts:831`）已有 `id / name / price / track / level / audience`，
研發（CAFE-16～18）已經會解鎖新品項。**只需要補兩個欄位**：

```ts
interface CafeMenuItem {
  // ...既有欄位不動
  recipe: Partial<Record<CafeIngredientId, number>>;  // 新：一份要用掉哪些料、各幾單位
  baseWeight: number;                                  // 新：基礎熱門度（選品權重）
}
```

### ✅ P1 實作結果：重訂後的原料單價

初版提案的配方（咖啡豆 ×1 等）在舊單價下毛利落差過大（咖啡 56% vs 烘焙 28%）。
實作時改成 **低單價 × 多單位**，用整數粒度換到「13 個品項全部落在 45～60%」：

| 原料 | 舊單價 | **新單價** | 舊常備量 | **新常備量** | 生鮮 |
|---|---|---|---|---|---|
| 咖啡豆 | $15 | **$4** | 20 | **130** | 否 |
| 牛奶 | $12 | **$3** | 15 | **24** | 是 |
| 麵粉 | $8 | **$3** | 10 | **52** | 否 |
| 奶油 | $18 | **$10** | 8 | **24** | 是 |
| 貓罐頭 | $25 | **$6** | 8 | **56** | 否 |
| 寵物鮮食 | $20 | **$5** | 6 | **24** | 是 |

常備量取自「成熟期（產能 40、人氣滿）實測 200 天的單日尖峰消耗再留餘裕」
（尖峰：咖啡豆 124 / 牛奶 12 / 麵粉 49 / 奶油 21 / 貓罐頭 51 / 寵物鮮食 21），
三種生鮮一律 ≤ 24，維持「照建議值玩 → 零缺貨、零損耗」的懶人路線（§4.3.1）。
配套把 `SPOILAGE_FREE_UNITS` 從 6 調到 15 —— 週轉量變大了，免損耗額度得跟著等比放大，
語意仍是「一天用得完的量不會壞」。

### 4.2 熱門度與顧客選品（零 RNG）

每位顧客用**決定性雜湊**選一項商品，權重 =

```
weight(item) = item.baseWeight
             × 客群修正(guest.intent / audience)
             × 天氣修正      // 冷天熱飲 ↑、熱天冷萃 ↑
             × 時段修正      // 早上咖啡 ↑、下午烘焙 ↑
```

雜湊取自 `顧客 id | 遊戲日 | 小時`，抄 `cafeGuests.ts` 既有的 `cafeGuestHash` 作法，
**不新增任何 `Math.random()`**（多一次亂數就會位移整個模擬序列）。

**玩家從哪知道熱門度？** ✅ **P3 已實作**：咖啡廳面板的「**銷售排行**」區塊
（`cafeSalesRanking()`）列出過去 7 個遊戲日各品項的賣出杯數與缺貨次數，由高到低。
這就是需求 1「視顧客購買的產品熱門度做補貨」的資訊來源 ——
**玩家不是被告知權重，而是從銷售紀錄自己讀出來**，這才是經營感。
缺貨次數用紅色徽章單獨標出（那是玩家正在流掉的錢），下方再補一行本週撲空總人次。

### 4.3 庫存、補貨與缺貨

**補貨時機從「日結後」移到「開店前」**（每日 10:00 前一刻）：

1. 依常備量計算缺口 → **立刻扣款進貨**（錢不夠就只補得起的部分）
2. 開店，帶著這批庫存做一整天生意
3. 20:00 關店 → 扣固定開銷 → 易腐品損耗結算

這個順序讓玩家**先付錢、後賺錢**，是「經營」與「領被動收入」的分野。

**缺貨處理（需求 1 的核心）**：

| 情況 | 結果 |
|---|---|
| 配方所需原料齊全 | 扣料、`money += item.price`、聲譽 **+**、日誌「有人點了拿鐵」 |
| 缺任一項原料 | **$0 收入**、聲譽 **−**、顧客立刻離場、日誌「有人想點拿鐵，牛奶沒了」 |
| 連續缺同一品項 | 該品項的 `baseWeight` 短期下修（客人不再期待）＋額外聲譽懲罰 |

第三條是刻意的：**放著不管會愈來愈糟**，這是「經營壓力」的來源。

#### 4.3.1 懶人路線必須維持可行（拍板 Q3）

使用者要求保留現在「設一次常備量就能放著」的路線，**作為低效但可行的選項**。
設計上這靠三件事保證：

1. **常備量沿用既有機制**（`state.cafe.standingOrders`），不改成「每天手動下單」。
   設一次就會一直照那份清單補貨
2. **`suggestedStandingOrders()` 要跟著菜單走** ✅ **P3 已實作**：面板的
   「**依上週銷量建議**」按鈕（`suggestStandingOrdersFromSales()`）一鍵把常備量草稿設成
   `ceil(過去 7 個遊戲日的單日尖峰需求 × 1.15)`。三個細節：
   - **尖峰而非平均**（週末客流是平日的 1.39 倍，用平均會週週缺貨）
   - **把 `missed` 一起算進需求**（依「實際賣出」補貨會讓缺貨自我實現）
   - **菜單上的原料有「至少兩份」的底線**，剛研發完的新品不會被建議成 0
   沒有可用歷史（剛開張／舊存檔沒有 `sales`）時整份 fallback 回內建建議值，
   **永遠不會算出全 0 或 NaN**
3. **偷懶的代價是「賺得少」，不是「會倒」**：
   - 均勻備貨 → 熱門品偶爾缺、冷門品偶爾爛掉 ⇒ 毛利被兩頭吃掉
   - 估計落在**勤勞玩家的 60～70% 淨利**，仍為正值
   - 但**不足以支撐擴張**（雇人、升招牌都要現金）⇒ 想長成主業就得開始盯

⇒ 懶人玩得下去，但停在「開張期～成長期」；想走到名店期必須真的經營。
這與 §4.7 的成長曲線是同一件事的兩面。

### 4.4 開店 / 關店與一日節奏

| 遊戲時間 | 事件 | 畫面 |
|---|---|---|
| 09:00 | 進貨扣款 ✅ P3 | `cafeRestockPass()`；一天只扣一次（`sales[].restocked` 旗標） |
| **10:00** | **開店** | 招牌亮起、門打開、一樓地板恢復正常亮度 |
| 10:00–20:00 | 每小時 `ceil(當日客流 / 11)` 位顧客進場 | 逐位走進來點餐（見 §4.5） |
| **20:00** | **關店** | 顧客清場、門關、招牌熄、一樓轉暗 |
| 20:00 | 日結（實作掛在午夜換日） | 扣固定開銷 $370、**對打烊後剩餘庫存**算易腐損耗、寫 history、推日誌 |

非營業時段一樓是暗的、空的 —— **玩家一眼分得出「營業中」和「打烊」**，這本身就是需求 2。

### 4.5 看得見的消費（需求 2 的核心）

`GuestAgent` 的 phase 從 `entering → seated → leaving → departed`
擴充成：

```
entering  → ordering → (成功) served → seated → leaving → departed
                     → (缺貨) refused →                   leaving → departed
```

| phase | 畫面演出 |
|---|---|
| `entering` | 從店門走向**吧台**（固定位置） |
| `ordering` | 站在吧台前，頭上泡泡顯示**他要點的商品圖示**（不再是抽象的意圖符號） |
| `served` | **`+$34` 綠色浮字**從頭上升起、金錢數字跳動 |
| `refused` | **紅色 ❌ 泡泡**、聲譽數字閃一下紅色 |
| `seated` | 走到**固定座位**坐下（真的坐在椅子上，不是站空地板） |
| `leaving` | 起身走向店門 |

**意圖泡泡一併重做**（解決使用者「不知道標誌什麼意思」）：
- 點餐時顯示**商品圖示 + 價格**，不是抽象符號
- 「想認養寵物」「想租房」兩種可互動意圖，改成**帶文字標籤的醒目提示**，
  並在咖啡廳面板同步列出（現在只有面板有，畫面上的符號沒人看得懂）

### 4.6 座位：不鎖，但座位本身就是容量（拍板 Q4）

現況的衝突：顧客有 6 格 `CAFE_GUEST_PREFERRED_SEATS`，而開張贈品**刻意避開它們** ⇒
顧客站在空地板上。

**廢除 `CAFE_GUEST_PREFERRED_SEATS` 這張硬編座位表**，改成
**「顧客坐在玩家實際擺的椅子上」** —— 座位不是寫死的座標，而是查 `placements`：

```
內用席次 = 一樓四區裡 `seat` 欄位不為空的家具數量
（`seat` 欄位是 2026-08-03 CAFE-20 renderer 那批已經加好的，直接沿用）
```

顧客動線：**店門 → 吧台（固定 (3,38)）→ 任一空席 → 店門**

這個設計同時解決四件事，而且**不需要任何 UI 鎖定邏輯**（拍板要求「以好做為主」）：

| | |
|---|---|
| 看得到入座 | 顧客坐在真的椅子上，不再站空地板 |
| 可以拆 | 拆了不會壞，只是**席次變少** |
| 拆掉有代價 | 席次不足 → 後到的顧客**只能外帶** |
| 家具有意義 | 買椅子 = 買容量，和既有的氛圍加成（`cozy + style` → 客流）疊成兩條回饋 |

**外帶的代價**（這是「拆掉有後果」的具體化）：
- 外帶客**只點飲料，不點烘焙/寵物餐** ⇒ 客單價明顯較低
- 外帶客**不貢獻氛圍評價**，聲譽只給一半
- 全店零席次 = 純外帶店，能活但收入明顯較差，且畫面上永遠看不到人坐著

⇒ 玩家會自己發現「多擺幾張椅子比較賺」，不需要我們鎖住任何東西。

`src/sim/cafe.ts` 的 `SPOILAGE_FREE_UNITS` 註解裡。

2. **客流本來就被產能夾住**（`cafeCrowd()` 的 `min(base, capacity)`），所以
   「人手不足 ⇒ 客流暴增到排爆」不會發生；隊伍長度大致是
   `每小時到客 − 同時服務人數`。**在席次是瓶頸時**（產能固定）雇人確實會讓隊伍變短；
   在員工是瓶頸時，雇人同時抬高客流，隊伍不會消失而是換成更多營收。

### 4.10 地板分區產生機能差異（A 批，2026-08-16 實作）

一樓有四個區域（`cafe_floor` / `cafe_counter` / `cafe_pet` / `cafe_back`），
但在本批之前它們只是**底色不同的地板**：家具擺哪裡都只算同一份氛圍加成
（`cafeAmbiancePoints()` 的 `cozy + style`），玩家沒有任何理由把冷藏櫃放進後場。
本批給四個區域各自的機能，並且只用一條規則：

> **家具擺在對的區才有機能效果；擺錯區只剩氛圍（`cozy + style`）。**

**擺錯區不倒扣、不是失敗狀態** —— 氛圍照算，只是少拿一份機能。
`cafeAmbiancePoints()` 因此**一行未改**（改了客流乘數就會漂移）；
機能一律走 `placements.ts` 尾段新增的、**區域受限**的查詢函式。

| 區域 | 查詢函式 | 機能 |
|---|---|---|
| `cafe_back` 後場 | `cafeBackStoragePoints()` | 庫存容量上限 = `min(4000, 360 + 點數 × 40)` |
| `cafe_pet` 寵物區 | `cafePetComfortPoints()` | 寵物停留更久 + 認養詢問更容易出現 |
| `cafe_counter` 吧台區 | `cafeCounterSpan()` / `cafeCounterTechPoints()` | 同時服務人數 = `1 + 吧台寬度 + floor(tech / 3)` |

#### 三條機能的推導

- **後場選「容量」而不是「降損耗」**。降損耗會撞上既有投資項「大型冷藏」，
  而且 `SPOILAGE_FREE_UNITS = 23` / `SPOILAGE_RATE = 0.9` 是不等式 `(24 − F) × R < 1`
  的唯一解 —— 任何額外的免損耗來源都會把 §4.7 的「備太多反而虧」推回正值。
  底量 360 高於建議常備量總和 310 ⇒ **開張期玩家永遠碰不到上限**，
  補貨行為與本批之前逐字相同；名店期常備量約 900，需要「貨架 ×2 + 木箱 ×1」（$13,600）。
- **寵物區兌現了兩句一直沒接線的投資項說明**：貓跳台與軟墊的「寵物停留更久、
  認養詢問更容易出現」、店面招牌的「租屋詢問更容易出現」。`intent` 不參與結帳
  ⇒ **營收零影響**，改變的只有面板上會出現哪一種詢問卡。
  判準用 `category === "ambiance"` 而不是白名單：桌椅是 `seating`，
  玩家不能把桌椅塞進寵物區刷分。
- **吧台的「+1」是刻意的**：吧台後方的收銀／出餐口一定存在，所以「拆光吧台」
  退化成 1 個服務位而不是 0（同 `CAFE_TAKEAWAY_CAPACITY` 的哲學）。
  tech 這一項兌現了濃縮咖啡機的 `tech 3`；冷藏櫃的 `tech 2` 擺在後場不生效 ——
  **那正是分區規則本身**。必須區域受限，否則玩家可以在主廳拉一條 14 格的吧台。

#### 這一批解掉了 §4.9 的張力 ①

上面「P4b 實作後發現的兩條張力」第 1 條（同時能結帳的人數被吧台寬度夾住、
雇第 5 位以上的員工不會再增加同時服務人數）在本批得到正式答案：
**服務位就是產能公式的第三條腿**，`cafeCapability()` 用
`min(staffCount, stations)` 算出真的做得出杯子的人數，面板用 `idleStaff`
明說「有 N 位沒有吧台位置，加寬吧台才能讓他們上工」。
`cafeStaffSpots()` / `cafeCounterSpots()` / `cafeQueueTiles()` 的 lane 展開序
改讀**整個連通塊**，所以第二座吧台一接上去，員工站位與隊伍就自動變寬，
沒有第二套幾何。

⚠️ **這是唯一會咬既有存檔的改動**（使用者已核可）：雇 4 人以上、吧台仍是贈品那座的
存檔，產能 `4 × 26 = 104 → 3 × 26 = 78`。收斂性有既有論證背書，不會死亡螺旋，
而且面板會直接告訴玩家該做什麼。

#### 刻意不接：家具的 `tier` 屬性

咖啡廳的 13 件家具**每件功能唯一**，沒有「同功能不同 tier」的組
（不像三樓的沙發/電視/浴缸/書桌各有 budget/standard/premium 三檔）。
把 `tier` 接進咖啡廳的機能只會變成**雙重計價** —— 同一件家具的價格已經
反映在它的屬性點數上，再按 tier 乘一次沒有任何設計意義。
**本結論不留待辦**，日後不必再評估一次。

### 4.11 常客系統（B 批，2026-08-16 實作）

> **「有人記得你，也有人被你記得。」**

在本批之前，咖啡廳的每一位顧客都是**一小時的臨時體**：`CafeGuest.id` 由
`(seed, sequence, arrivedMs)` 雜湊而來，天生每次不同；下一個整點他就從陣列裡消失，
玩家永遠不可能對任何一位客人產生印象。本批讓其中 **6 位**變成跨日認得出來的人。

#### 為什麼身分鍵是「姓名」而不是 id

`CafeGuest.id` 含 `arrivedMs`，**設計上就不可能穩定**。唯一穩定的識別是
`content/cafeGuestNames.ts` 的姓名池 —— 而且這個專案早就採用了
「**同名 = 同一個人**」的語意：`cafeGuests.ts` 的 `CAFE_GUEST_GENDERS` 註解寫著
「只能 append，改動既有對應會讓舊存檔裡的同名應徵者換性別」，也就是說姓名
在這個系統裡**已經是身分**了，本批只是把這條既有語意用出來。

代價是「同名撞人」：兩位不同的臨時顧客抽到同一個姓名時會被算成同一個人。
這正是本批把姓名池從 32 擴到 **64** 的理由（純 append，前 32 筆逐字未動）——
單一姓名的日到訪期望從 0.8 降到 0.4 次，撞人率減半，同時 6 位常客佔比從 19% 降到 ~10%，
名店期（一小時 12 位客人）才不會變成「來來去去都這幾個人」。

#### 為什麼回訪節奏「不乘客流」

直覺的寫法是「每位顧客有 X% 機率是常客」，但那會被客流放大：
名店期 130 客/日 × 12% ≈ **一天來 15 次**，常客立刻從熟面孔退化成背景板。

改成與客流完全脫鉤的**每小時抽籤**：

```
每個營業小時 18% 機率有一位常客上門 → 11 小時 ≈ 2.0 位/日（開張期與名店期一致）
⇒ 6 位常客各約 3 天回訪一次
```

3 天這個數字不是湊出來的，它與**好感寬限 `CAFE_REGULAR_GRACE_DAYS = 3` 對齊**：
正常經營時常客永遠落在寬限內 ⇒ **好好開店的人不會掉好感**；
只有真的怠慢（關店、天天缺貨、離線太久）才開始每日 −1。這條對齊讓好感變成
「你有沒有在照顧這間店」的量尺，而不是一個會自然衰減的體力條。

抽籤只依賴 `(day, hourIndex, 排序後的名冊)`，零 `Math.random()`
⇒ **線上逐時跑 11 小時 = 離線 `syncToNow()` 一次補 11 小時**，
論證與 `cafeHourlyGuestCount()` 完全相同。名冊固定以 `(sinceDay, name)` 排序，
所以「今天輪到誰」與陣列插入序、存檔往返、升格順序都無關。

#### 「帶朋友」為什麼改成救回一位放棄客

原案是「高好感常客有 35% 機率多帶一位顧客進來」。**那會打破兩條已經咬合的不變式**：

1. `crowd.guests = min(base, capacity)` —— P4a 建立的產能上限語意；
2. 「當日營收 = Σ 每位顧客實際賣出」—— 整個 P1 重設計的唯一主張。

多生一位客人等於在產能上限之外憑空開一條金流管道，兩條同時破功。
改成 **該小時 `abandonCount −= 1`**（把本來會排到放棄的一位留下來）之後：

- 零產能突破（`crowd.guests` 一位都沒動）、零新金流管道（那個人本來就不在營收裡）；
- 玩家**看得見**：人龍裡少了一個轉身離開的背影；
- 只在「已經有人排到放棄」時才生效 ⇒ 生意還沒好到會漏客人的店感覺不到，
  這反而是正確的：帶朋友的價值本來就該在店最忙的時候才顯現。

#### 三個機能效果與平衡上界

| 效果 | 條件 | 內容 | 平衡上界 |
|---|---|---|---|
| ① 老樣子 | 常客到店 | 直接點 `itemCounts` 最高的那一項；沒有紀錄時改用他的 `taste` 當客群修正 | 客單價位移 < $1/客 ≈ **$0** |
| ② 小費 | `affection >= 60` | 結帳 `revenue += $3` | 2 位/日 × $3 = **+$6/日**（開張期淨利 +$109 的 5.5%） |
| ③ 帶朋友 | `affection >= 80` 且該小時抽中 35% | 該小時 `abandonCount −= 1` + 一則敘事 | 聲譽最多 +0.7/日，且只在已經有人放棄時 |

**口味 `taste` 綁姓名不綁日期**：`雜湊(cafe-regular-taste|姓名) % 3`，
所以同一個人在任何存檔、任何一天都同一個口味。這順手解掉舊設計的一個彆扭 ——
`chooseCafeMenuItem()` 的口味偏好本來是「每位顧客當場雜湊出來的」，
不存在任何人身上，玩家永遠感覺不到「她就是喜歡甜的」。有了固定口味之後，
**針對常客備料**才成為一個玩家講得出口的行為（「她天天點拉花拿鐵，牛奶不能斷」）。

`chooseCafeMenuItem()` 新增的 `preferTrack?` / `forceItemId?` **兩個參數都是選填，
省略 = 逐項等於今日輸出**，既有呼叫端與 `cafe-menu-test` / `cafe-per-guest-test` 零改動。

#### 升格、衰退與流失

```
成功被服務 → 不是常客：candidates[姓名]++（一天最多一次）
             累到 3 且名額未滿 → 升格，推一則日誌
           → 已是常客：visits++、好感 +4、itemCounts[品項]++（一天最多一次）
缺料撲空   → 好感 −6（不算來訪日，不推遲衰退計時）
日結       → 超過寬限 3 日才每日 −1
流失       → 好感 <= 0 **且** 14 日未來（兩個條件都要）
```

- **「一天最多一次」是必要的**：名店期一天 130 位客人，沒有這道閘門的話同一個姓名
  一天就能累積好幾次，3 次的門檻形同虛設。常客靠自己的 `lastVisitDay` 擋；
  候選人沒有那個欄位，所以存檔多了一個 `regularCandidateDays`（姓名 → 上次計數的遊戲日）。
  **它必須進存檔**：若改用模組層的暫存 Set，「線上逐時 vs 離線一次補」就會分岔，
  那是本專案最在意的離線一致性破口。
- **候選人每 7 個遊戲日全體 −1、歸零者移除**：3 次必須在**滾動窗**內累積，
  不會出現「兩個月前來過一次」的殭屍候選人，常客因此永遠代表「最近真的常來」。
- **刻意不因「撲空太多次」直接流失**。那會把一次缺貨變成永久損失，
  也就是整份設計一直在避免的失敗狀態；缺貨的懲罰留在聲譽那條路（−2/人）就夠了。

#### 存檔與安全底線

- `CafeState` append 三個欄位（`regulars` / `regularCandidates` / `regularCandidateDays`），
  **`SAVE_VERSION` 維持 10**（additive + 舊檔補安全值，先例是 `sideArc` / `arcHistory`）。
- **刻意不回填舊存檔**，理由同 `MIGRATIONS[8]`：回填假資料只會讓面板顯示玩家
  從未發生過的事。約 4~5 個遊戲日就會出現第一位常客。
- 🔴 **安全底線**：常客**不進 `state.runtimes`**、**不建 `relationships`**、
  **不參與戀愛線／同居／未成年判定**。他們只是 `state.cafe` 底下的一筆觀察資料，
  整個社交/戀愛子系統的入口（`runtimes` / `relationships`）一個都碰不到 ⇒
  既有硬規則不需要、也無從被繞過。常客要走進租客的人生仍然只有一條既有的路：
  以 `intent === "rent"` 的顧客身分被帶看、經 `recruit.ts` 成為應徵者、再入住 ——
  那條路上的所有把關一行未改。這段話也寫在 `sim/cafe.ts` 第 16 節的檔頭註解裡。

#### 面板：常客是觀察物，不是決策卡

第 10 個可收合區塊，**沒有任何按鈕**。每列純文字（同認養卡／租屋卡的作法，
不做頭像元件）：`☕ 方雨晴 · 來訪 12 次 · 老樣子「經典拉花拿鐵」 · [好感條 72] · 3 天前來過`，
好感 >= 80 前綴換成 🌟，14 天沒來顯示「快要失聯了」。
認養卡／租屋卡上若該顧客是常客，`<small>` 多一句「（常客・來訪 N 次）」——
**不改任何星等／開價算式**。

不加決策的理由：咖啡廳已經有兩張會過期的詢問卡，再多一張只會讓玩家在掛機遊戲裡
多一件「不處理就虧」的事。常客應該是**你經營出來的結果**，不是又一個待辦。

### 4.12 打烊後的租客聚會（CAFE-21 的內容端，2026-08-16 實作）

> **「店關了，燈留一半，樓上的人下來坐。」**

CAFE-21 早就把 `GroupSceneVenue` 的 `"cafe"` 做好了（`groupScene.ts` 的
`cafeTiles()` / `cafeAnchorFor()`），但**全專案零呼叫者**——所有聚會一律
`lounge` / `rooftop`，能力等於沒有。本節補的是內容端。

#### 為什麼是「打烊後」而不是營業時間內

1. **畫面會打架**。`cafeTiles()` 只看 grid 與 `currentBlocked()`，
   完全不知道 `guestAgents` 的座位／吧台／人龍格與 `staffAgents` 的站位在哪。
   營業時間內開場，3～4 位租客極可能站進排隊隊伍或客人已入座的位置上。
   要修就得讓 `groupScene` 認得顧客佔用表——那是一套新的耦合，而且修好了畫面
   仍然是「自己人在自家店裡插隊」。反過來，`cafeBusinessOpen()` 為 false 時
   顧客與店員 agent 都已清場（`FloorMap.vue` 的 `staffAgentSignature`、
   `tick.ts:601` 的離場），整層地板是空的，`cafeTiles()` 的既有邏輯直接就對。
2. **白天的畫面已經有了**。CAFE-20（`routine.ts` 的 `at_cafe`）本來就會讓租客
   各自下樓坐咖啡廳。缺的是**群體**的畫面；「打烊後自己人包場」和白天的散客感
   剛好互補，是一個新畫面而不是同一個畫面加人數。
3. 時段取 `CAFE_CLOSE_HOUR + 1 = 21:00`（含尾的營業時段之後第一個整點）。
   七種作息原型有五種此時仍在樓裡，`scheduledCommunityPass()` 本來就會把答應
   參加的人拉回來入鏡。

#### 為什麼不併進 `COMMUNITY_EVENTS`

`communityPass()` 是 `eligible[Math.floor(rng() * eligible.length)]`，
把兩件咖啡廳事件塞進同一個陣列，會讓既有 11 件的相對機率從 1/N 掉到 1/(N+2)
——**那就動到 lounge / rooftop 的平衡了**。改成獨立池 `CAFE_COMMUNITY_EVENTS`，
只在**當天沒有任何其他社群／群體事件發生時**才補抽一次（`rollCafeGathering()`）：
既有事件的絕對與相對觸發率**完全不變**，咖啡廳只吃原本空著的日子。

| 事件 | 條件 | 時段 | layout（錨點） | 效果 |
|---|---|---|---|---|
| `cafe_afterhours` | 平日 · `need` 2 人 · 冷卻 3 日 | 21:00 | `table`（吧台前） | 兩兩好感 +2、心情 +4、壓力 −5 |
| `cafe_weekend_night` | 週末 · `need` 2 人 · 冷卻 3 日 | 21:00 | `cluster`（座位區中央） | 兩兩好感 +3、心情 +5、壓力 −6 |

補抽機率 `CAFE_GATHER_CHANCE = 0.3`。兩件依 `isWeekend()` 互斥，所以任一天
最多只有一件可選，節奏約每 6～7 個遊戲日一場。

**2026-08-27：`need` 從 3 降到 2。** 初版設 3 人，而**種子局只有兩位租客**
⇒ `rollCafeGathering()` 的 `present.length >= e.need` 直接濾掉，這兩件事件
**在種子局永遠不可能觸發**，玩家從沒看過。兩件都要降：只降平日場的話，週末會
兩邊都失格（平日場被 `when` 擋、週末場被 `need` 擋），白白少掉一週 2/7 的機會。
`scheduledCommunityPass()` 的 `parts.length < ev.need` 讀的是 `ev.need`，自動跟著走。

> ⚠️ **`need = 2` 的取消風險**（已知、本批未修）：`scheduledCommunityPass()` 會
> filter 掉 `pendingEvent` 的人。兩人場只要任一人在演出當下被掛上待決事件，整場
> **靜默取消**，而冷卻早在 `scheduleCommunityEvent()` 排程時就蓋章了 ⇒ 白燒 3 個
> 遊戲日冷卻。修法會動到既有 lounge / rooftop 事件的冷卻語意，需獨立一批處理。

#### 零漂移論證

`rollCafeGathering()` 第一行是 `if (!state.cafe.open) return false;`——未開張
**連一次 `rng()` 都不抽**，呼叫端後續的亂數序列與本批之前位元級相同。
無頭的 balance 快照局永遠不會開張咖啡廳 ⇒ 快照零漂移（實測一致）。
文案選句沿用 `sceneIndex()` 的既有決定性雜湊，開演過程零 `Math.random()`。

#### 畫面：橫幅要跟著樓層走

`FloorMap.vue` 原本的現場橫幅寫死 `v-if="eventScene && isTenantFloor"`。
`cafe` 場地的走位在一樓，掛在三樓會變成「橫幅寫著現場、畫面上一個人也沒有」。
改成 `sceneOnThisFloor`：`cafe` 只在一樓頁面顯示，`lounge` / `rooftop` 維持只在
三樓顯示，前綴 `☕ 店裡`，並壓在 1F viewport 最上緣避免蓋住 41～44 列的演出。

### 4.13 讓 AI 看見咖啡廳（D 批，2026-08-16 實作）

> **「AI 只能讀咖啡廳，一個字都寫不回去。」**

在本批之前，`NarrateCtx`（`narrate.ts`）、worker 的鏡像介面與 `buildPrompt()`
**三處零咖啡廳欄位**。唯一接點是硬編模板日誌（`cafeDailyLine()` / `cafeOrderLine()` /
`cafeRegularLine()` / `cafeRegularFriendLine()`），而 `pushCafeLog()` 把它們全掛在
「id 排序第一位」的在住租客身上 ⇒ **只有一位租客的 AI 看得到樓下發生什麼事**。

#### 四個拍板決定

1. **咖啡廳 context 送給全體在住租客**（不是每日輪一位）。咖啡廳在所有人樓下，是共享環境；
   現行掛第一位的作法本來就脆弱（那位退租，日誌就整批跳人）。若實玩後發現蓋台，
   降級開關是改成雜湊輪一位（單行改動），本批不做。
2. **接受常客姓名收緊**（NFKC → 字元白名單 → 夾 12 字）。這是**補既有漏洞**，不是新規則。
3. **「去換行」本批只做新欄位**，不擴及 `clampStr` 的所有字串欄位——那會改變既有 prompt
   內容、可能影響既有敘事品質測試。全域缺口另立 `docs/待辦.md` 一條。
4. **AI 只能讀咖啡廳，零寫入面。**

#### 資料模型：送「已組好的短句」而不是原始數值

`NarrateCafeCtx`（`narrate.ts`）：`brief`（≤48 字）、`trend`（`up`/`flat`/`down`）、
`regulars`（≤2 條、每條 ≤28 字）、`ops?`、`pets?`（各 ≤28 字）。`NarrateCtx.cafe?:`
是 additive，舊 ctx 缺省 = 不進 prompt（同 `weather` / `wish` 慣例）。

為什麼不送原始數值：測試與領域知識留在 app 端（`cafe.ts` 已有全套純函式與 12 支測試）；
離線 fallback 共用同一份素材；worker 的消毒面因此收斂成「夾長 + 去換行 + enum 白名單」，
不需要理解咖啡廳語意。**最大 payload 約 200 字**，距 `MAX_BODY`（16KB）餘裕極大。

素材來源全部零新狀態、零亂數（`cafe.ts` §17，選句一律走既有的 `lineHash()`）：
`brief` 取 `sales` 最後一筆（空手離開 ≥4 → 忙碌 → 沒客人，三分支）、`trend` 取 `history`
末筆對前三筆平均（±15%）、`regulars` 取 `sortedCafeRegulars()`（今天來過的 → 快失聯的）、
`ops` 取研發中 → 後場塞滿 → 吧台太窄、`pets` 取三個遊戲日內的咖啡廳顧客認養。
`cafe.ts` **仍然不 import `placements`**：後場容量與吧台位由 `narration.ts` 算好當參數餵進去。

#### 🔴 消毒三層（缺一不可）

| 層 | 位置 | 做什麼 |
|---|---|---|
| 一、存檔載入 | `gameState.ts` 的 `sanitizeCafeRegularName()` | NFKC → 字元白名單 → 夾 `CAFE_REGULAR_NAME_MAX = 12`；清乾淨後為空 ⇒ 整筆丟掉 |
| 二、app 端組 ctx | `narration.ts` 的 `buildCafeNarrateCtx()` | 每欄過一次 `sanitizeContextLine()`；`brief` 為空 ⇒ 整個 `cafe` 不送 |
| 三、worker 端 | `worker/index.ts` 的 `clampCafeCtx()` | 同一份 `sanitizeContextLine()` 再夾一次 + `trend` enum 白名單 |

新的 `sanitizeContextLine()`（`narrativeQuality.ts`，**app 與 worker 共用一份實作**）：
NFKC → 去 `\p{C}` → 空白（含換行）壓成單一空格 → 去 `[ ] 【 】` → 去行首 `- # >` → 夾長。

**去換行是最重要的一項**：`buildPrompt()` 用 `\n` 串行、`[...]` 當區塊標記、`  - ` 當條列符，
一個帶換行的字串足以偽造 `[今日唯一主線…]` 這樣的假指令行。既有的 `clampStr()`
只做 `.slice()`，擋不住。刻意**不**沿用 `sanitizeReasonText()`——它會做逗號子句語意去重，
對單句是破壞性的。

第三層為什麼不可省略（「不信任前端」有真實繞道）：`state.pendingDiaries[].ctx` 是**整份**
存進 localStorage 的 ctx，`persistence.ts` 載入時完全不消毒，`resumeDeferredDiaries()`
之後原封 POST 回 `/api/narrate`。

#### 🔴 安全底線

- **本批新增零個寫入面**：`NarrateResult` 不新增欄位、`applyDiaryEffects()` 一行未改、
  AI 輸出的 JSON schema 不新增 key、`narration.ts` 只讀 `state.cafe` 永不寫。
  四項都有原始碼掃描斷言釘住（`cafe-narrate-ctx-test.ts` 第九節）。
  論證同 `sideArc` / `wish` 的既有取捨：**進度由本地決定，AI 只當動機素材**；
  讓 AI 回寫庫存／聲譽／好感只會得到「AI 宣布好感上升、隔天算式扣回去」的自相矛盾。
- **新增硬不變式「熟客名字 ∩ 租客名字 = ∅」**：組 `regulars` 時濾掉任何與現任租客同名的常客。
  動機一，常客可循 `intent === "rent"` 真的搬進來（那時他就**是**租客，該出現在 `neighbors`）；
  動機二，特邀租客讓玩家自訂姓名，可能與常客池撞名。效果是 `applyRelNudge` 的
  「名字出現在 `todayLog`」條件永遠無法被 `ctx.cafe` 這條路滿足。
- **未成年**：`CafeRegular` 與 `NarrateCafeCtx` 都沒有年齡／性別／取向欄位，
  既有「未成年排除戀愛線」規則無從被咖啡廳這條路繞過（掃碼斷言釘住）。

#### 四道防線：為什麼不會蓋台

1. **`focus` 一行未改**——新 `ctx.cafe` 不參與主線計算，咖啡廳只有在日誌真的落進那位
   租客的 `todayLog` 時才可能成為主線，與本批之前完全相同。
2. 咖啡廳四行放在 `[背景資料—只供理解，除非今天片段有新進展，不可直接寫成今日事件]`
   區塊內，繼承一條已經在運作的守則（`relationships` / `neighbors` 就靠它沒有蓋台）。

## 九、可見性批次（2026-08-25）— 讓玩家看得見自己被什麼卡住

> 需求來源：使用者實玩回報「**投資與研發都沒有效果、家具可有可無**」。
> 本批**純可見性、零平衡漂移**：不改任何算式、不改任何數值、不改控制流。

### 9.1 診斷：三個「數學上的精確 0」

唯讀調查以公式重算使用者的存檔，結論不是「數值失衡」，而是**資訊缺口**：

| 現象 | 實際成因 |
|---|---|
| 三級招牌 + 戶外座位（$225,000）毫無感覺 | 服務位 = 1 ⇒ 產能 36 單／日，而想上門的有 66～100 人。`guests = min(base, capacity)` ⇒ 邊際效益**精確等於 0** |
| 家具可有可無 | 氛圍已 91 點、上限 60 點 ⇒ 超出的 31 點（≈$28,000 的家具）對客流貢獻**精確等於 0** |
| 「客人好像變少了」但看不出證據 | 每天約 64 位客人在資料層無聲蒸發。放棄門檻是每小時 8 人，他每小時只溢出 5.8 ⇒ 畫面上**一位「排到放棄」都不會演** |

⇒ 玩家不是買錯東西，是**遊戲沒有告訴他被什麼卡住**。修法因此全在 UI 與一個新紀錄欄位。

### 9.2 為什麼主數字是「一般日」而不是「今天」

當日客流被天氣（0.7～1.15）與星期（0.9～1.25）推到 ±38% 之間跳。玩家週一看到
「買招牌沒用」、週六看到「有用」，會直接推翻整個面板的可信度。兩張表的加權平均分別是
0.99 與 1.021，**取 1.0 的長期誤差約 1%** —— 主數字用它，當日值只放小字。

### 9.3 `cafeTypicalBase()` 為什麼不是第二份算式

拍板「**不重構 `cafeCrowd()`**」（sim 熱路徑，改取整順序＝平衡快照漂移風險）。
但「另寫一支 UI 專用算式」的代價是兩份公式各自漂開。解法是**讓它就是 `cafeCrowd()`**：

- **天氣**：`CAFE_WEATHER_MULTIPLIER.cloudy` 本來就恰好是 `1.0`，直接餵
- **星期**：七格裡沒有 1.0（1.25／0.9／1.05）。但 `cafeCrowd()` 對 `signLevel`
  **不取整**，而 raw 對 signLevel 是線性的 ⇒ 把等級**先除以該格的係數**再餵進去，
  乘回來與「星期係數 = 1」在數學上完全等價；浮點尾差（相對 ~1e-15）由 `cafeCrowd()`
  內原本就有的 `quantize()`（`toFixed(6)`）吸收，遠低於 5e-7 的取整邊界

⇒ 兩式不可能漂開，因為只有一式。`cafe-bottleneck-test.ts` 仍逐週日 × 196 組反覆驗這條等價
（含 raw 剛好落在 `.5` 取整邊界的那一組）。

### 9.4 投資文案用「差分」，不用查表

```
extraOrders = min(baseAfter, capacityAfter) − min(baseBefore, capacityBefore)
```

兩側都**再呼叫一次真的 `cafeCapability()` / `cafeTypicalBase()`**，只是把 id 加進
「假設已買」的清單。文案因此不可能與公式漂開 —— 它就是公式本身；招牌那條「精確 0」
的條件正是 `base >= capacity`（與 `cafeBottleneck().crowdBlocked` 同一個判斷式），
差分自然算出 0，不需要任何特例。戶外座位（只在晴天 +15%、不動產能）也走同一條差分：
把 `1 + CAFE_OUTDOOR_SUNNY_BONUS` **折算回等級軸**，避免多做一次獨立的取整。

### 9.5 `turnedAway` 為什麼不會漏記（early-out 一行未動）

`tick.ts` 的 `if (count <= 0 && abandonCount <= 0) return;` 刻意不碰。它不會漏記：
`turnedAway > 0` ⇒ `base > guests` ⇒ `guests === capacity`，而 `capacity >= 10`
（席次腿下界 `CAFE_TAKEAWAY_CAPACITY`；員工腿下界 `1 × 26`）。
`cafeHourlyGuestCount()` 用累積差分攤到 11 小時，`total >= 11` 時每小時的增量必 `>= 1`
⇒ 永遠走不到 early-out。唯一的邊界是 `capacity === 10`（玩家把椅子全賣光、只剩外帶），
那種店每天至多漏 1 位。**完整推導寫在 `tick.ts` 該行上方的註解裡**，測試另有
「Σ 11 小時 === base − guests」與「線上逐時 === 離線一次補」兩條把關。

累加用**兩個 `cafeHourlyGuestCount()` 相減**而不是 `cafeHourlyGuestCount(base − guests, h)`：
前者兩邊的取整誤差在小時之間互相抵銷，後者會多算/少算幾位。

### 9.6 已知取捨（實作時刻意不修）

1. **`base` 是波動值** —— 用「一般日」當主數字解掉，三格第一格永遠標「一般日」
2. **投資 chip 會在邊界翻面** —— 判定全踩整數且與天氣星期脫鉤，唯一慢速漂移源是
   `popularity`。跨界線時翻面是**真的狀態改變不是抖動**，因此**刻意不加 CSS transition**
3. **商店提示只在咖啡廳分頁** —— 三樓沙發搬進一樓仍會加氛圍分但租屋分頁不提示；
   換來不打擾租屋購物情境
4. **大型冷藏用 `standingOrders` 估損耗會高估** —— 文案寫「**最多**每天壞 N 單位」，
   blocked 那一側是嚴格正確的（常備量本身就進不了損耗門檻，實際庫存只會更低）
5. **服務位 = 1 與開張贈品對不上** —— `CAFE_STARTER_PLACEMENTS` 預設給 3，
   服務位 1 只會出現在玩家賣掉／搬走吧台或舊存檔。文案因此**特別涵蓋這個特例**
6. **🥐 流失日誌佔 `rt.log`（cap 60）一格** ⇒ AI 敘事素材少一格。已用三重節流壓到
   每遊戲週最多一則。**實玩後若覺得吵，這是本批第一個該砍的**，§9 的四個面板落點
   完全不依賴它

## 十、第三層研發批次（2026-08-25）— 客單價那條腿

§9 的可見性批次把「玩家被什麼卡住」畫出來之後，`cafe-growth-sim.ts` 的重量測給出
一個明確的歸因：名店期 Lv4 實測 **+$917/日**（設計目標 +$1,620），缺口 **100% 來自
客單價** —— 客流 118.6 已經**超過**設計值 110（單獨修正客流反而 −$169），
成本結構殘差只有 −$29。本批只動客單價那條腿，**客流與成本結構一格未動**。

### 10.1 診斷：三項研發的貢獻在數學上「精確是 0」

冷萃（$39）、每日磅蛋糕（$38）、奶油司康（$38）三項的**毛利額**恰好都是 **$19**，
而基礎菜單依 `baseWeight` 50/30/20 加權出來的毛利**也恰好是 $19.00**。
加權平均的性質：加進一個等於現行平均的樣本，平均一格不動 ⇒ 玩家花 $12,500
研發完這三項，成長曲線**在數學上精確沒有變化**，而且不報錯。

全部 10 項研發（$37,000）合計只值 **+$0.86/客**，其中三項是這樣的死項目。

**修法是調價不是改配方**：改配方會讓既有存檔的常備量、後場容量與損耗全部要重算。
慢萃 $39→**$41**、磅蛋糕 $38→**$43**、司康 $38→**$41**，三者仍在 45~60% 毛利帶內。
**只調價、什麼都不加的情況下**，名店期就從 85% → **92%** 淨租金（實測 +$1,000）。

回歸釘子在 `cafe-per-guest-test.ts`：**不准有任何品項的毛利等於基礎菜單的加權毛利**。

### 10.2 第三層三項：前置是招牌等級，不是設備

| | 季節限定豆 | 造型拿鐵 | 下午茶套餐 |
|---|---|---|---|
| 售價 | **$64** | **$58** | **$62** |
| 成本 / 毛利率 | $32 / 50.0% | $28 / 51.7% | $30 / 51.6% |
| 研發前置 | 手沖單品 | 拿鐵拉花 | 司康 |
| **投資前置** | **店面招牌（Lv2）** | **街角立招（Lv3）** | **霓虹招牌（Lv4）** |
| 研發費 / 天數 | $3,000 / 6 天 | $3,000 / 6 天 | $3,000 / 6 天 |

**用招牌而不是設備的四個理由**：① 招牌 Lv2 就是「成長期」的定義本身，掛設備的話
中段曲線補不上；② 一階一項的節奏，每升一級招牌就有一次「客單價跳一階」的體感；
③ 與 `cafe-growth-sim.ts` 的階段列一致（該腳本四階段的 `upgrades` 只有招牌）；
④ 擋得住開張期偷跑 —— 開張期沒招牌，一項都碰不到。

**研發費為什麼固定 $3,000 而不照「逐層加價」的慣例**：這是硬性數學約束，不是偷懶。
「名店期 105~115% 淨租金」反推出第三層整包的日增益上限約 $231/日 ⇒ 整包 60 天
回本的預算上限只有 $13,860；「成長期單項也要 60 天回本」更緊，上限 $3,600。
再貴就變成「解得開但永遠不划算」的死項目。**門檻改由貴到爆的招牌前置承擔**
（$30,000 / $60,000 / $110,000），不是研發費本身。

**實測逐項回本**（在它自己解得開的那一階段，單一變因只抽掉那一項）：
季節限定豆 **48.8 天**、造型拿鐵 **58.0 天**、下午茶套餐 **41.8 天** —— 三項都在 60 天內。

**刻意不做寵物線第三層**：寵物線總權重只佔 16%，再加一項只會稀釋自己，
驗算的名店期邊際只有 $11~25/日、回本 78~174 天，永遠追不上 60 天的門檻。

### 10.3 第七種原料：精品生豆（$14／單位，乾貨）

三項第三層要撐起 $58~64 的售價又守住毛利帶 ⇒ 需要 $28~32 的料錢。
用既有六種原料堆的話配方要 12~16 單位/份，每客平均用料 **3.90 → 4.30（+10%）**，
名店期常備量會頂破後場 920 上限 ⇒ 天天缺貨、曲線反而往下掉。
改吃 $14/單位的精品生豆之後每客用料 **3.90 → 3.91**，庫存腿一格不動。

- **乾貨** ⇒ 完全不碰 `SPOILAGE_FREE_UNITS = 23` / `SPOILAGE_RATE = 0.9` 那組唯一解
- 三項第三層**全部**用到它 ⇒「缺精品生豆 = 高價品全線停售」是乾淨可讀的新失敗模式
- 舊存檔沒有這個 key ⇒ `safeUnits()` 夾成 0，常備量顯示 0。**這是正確行為**

⚠️ **兩個副作用，都在本批一起修掉**：

1. **缺貨預估會叫玩家買用不到的東西。** `dailyDemand()` 是照 `perGuest` 對**全部**
   原料一律估的，它不看菜單 ⇒ 還沒研發第三層的玩家每天都會看到
   「⚠️ 依最近客流預估會缺：精品生豆」。已改成先過一次 `cafeIngredientMenuUse()`。
2. **後場底量的餘裕從 50 單位縮到 26。** 建議常備量總和 310 → **334**，底量仍是 360。

### 10.5 兩條既有護欄被刻意打破，以及替代品

**這一節是本批最需要被審的地方。** 兩條護欄的**前提**被新的設計目標推翻，
所以必須改寫；但替代品是「換一個角度守同一件事」，不是把數字放寬。

**(1) `cafe-menu-test.ts`「研發不是印鈔機：漲幅在一成以內」**
前提是「研發只值 +$0.86/客」的年代寫的，而那個 +$0.86 本身就是 §10.1 的 bug。
修掉 bug 之後漲幅本來就會變大（實測 +41%）。拆成兩條，第一條是新的且**razor-tight**：

- 🔴 **研發只准走客單價那條腿**：同樣的產能下**客流一人不動**（實測 36.0 → 36.0）。
  這才是「印鈔機」真正的形狀 —— 研發偷偷放大客流或產能。任何人日後讓某項研發
  影響客流／產能／人氣，這條立刻叫。
- 🔴 **產能腿（席次／人力／招牌）不投資，光靠研發到不了淨租金的一半**
  （實測 $461 = 42.6%）。菜單再貴也只是把 26 杯賣貴一點。

**(2) `cafe-p4a-growth-test.ts`「只買招牌的名店期到不了淨租金」**
這條**必然翻掉**：名店期預設到 115% 正是中控訂的目標。舊寫法用「到不了淨租金」
這條**絕對線**去表達「設備不是可選配」，而那條線已經被目標推翻。替代品兩條：

- 🔴 **設備的日增益必須撐得起它自己的價錢**：三件設備 $58,000、日增益 $461
  ⇒ 回本 **126 天**，斷言帶 **60~250 天**。這條直接綁在**真實售價**上而不是一個
  手挑的比值 —— 設備漲價或效果被削弱，回本天數會立刻跑出設計帶。
  （下界 60 天 = 不是無腦按鈕；招牌自己的設計帶是 56/102/175 天。）
- 🔴 **招牌不是萬靈丹**：升到 Lv4 但席次 6 / 零額外員工 ⇒ **$202/日 = 淨租金的 19%**。
  這是舊護欄那句話真正想講的產能腿約束，只是把「不投資設備」換成「不投資產能」——
  因為現在真正夾住玩家的是後者。
