## 一、為什麼要重設計：現況診斷

使用者實玩後的原話是「**他們有點餐嗎 他們有消費嗎 什麼都不知道**」。
追進程式碼後確認，這不是玩家沒看懂，而是**系統真的沒有把這件事做出來**：

| 現況 | 事實 |
|---|---|
| 畫面上的顧客 | 營業時段每小時用固定門檻 `CAFE_ARRIVAL_CHANCE = 55` 決定生不生，**純裝飾** |
| 你賺的錢 | 換日時由 `cafeCrowd(天氣 × 星期 × 招牌 × 產能 × 人氣 × 戶外座位 × 氛圍)` 一次算出 |
| 兩者的關係 | **完全獨立。看到 2 個人或 6 個人，跟今天賺多少一毛錢關係都沒有** |
| 菜單品項 | `CafeMenuItem` 結構已存在，但只被拿去算「平均客單價」，**沒有任何顧客點過任何一項** |
| 原料 | 只有 `perGuest` 平均消耗量，跟品項無關；補貨是「設一次常備量就三個月不用管」 |
| 顧客座位 | 有 6 格 `CAFE_GUEST_PREFERRED_SEATS`，但開張贈品**刻意避開**這六格 ⇒ 顧客站在空地板上 |
| 虧錢 | 幾乎不可能。滿客 26 人時淨利約 +$156/日；缺貨只讓人氣 −4，不直接損失 |

**核心問題**：咖啡廳是一台「換日時吐出一個數字」的黑箱，而畫面上的人是螢幕保護程式。

## 二、設計目標（對應使用者的四點要求）

1. **有經營的感覺** — 玩家要看著「哪些產品賣得好」決定補什麼料；**顧客買不到會不高興，不只賺不到錢，還會掉聲譽**
2. **每天開店關店，營業期間畫面上真的看到人點餐、消費**
3. **要有可能虧錢**
4. **咖啡廳座位可以固定**（使用者主動放寬，換取實作單純）

## 三、核心轉變

```
現在：  換日 → 一條公式 → 一個營收數字
        （畫面上的顧客與此無關）

改成：  每個營業小時 → 幾位顧客進場 → 各自點一項商品
                                    ├─ 有料 → 收錢、坐下、喝完離開
                                    └─ 沒料 → 不高興、$0、聲譽 −、轉頭就走
        當日營收 = Σ 每位顧客實際點到的商品售價
```

**畫面上發生的事，就是帳本上發生的事。** 這是整個重設計的唯一主張，其餘都是它的推論。

### 為什麼架構上做得到（關鍵技術前提）

`syncToNow()`（`tick.ts:944`）是**逐小時**補進度的 —— 離線 8 小時就跑 8 次 `hourlyTick()`。
所以「每小時結帳」**天生支援離線**，不需要另外寫一套批次對帳，也不會有「線上結果 ≠ 離線結果」的分歧。
這是本設計成立的前提，也是它比「即時逐秒模擬」務實的地方。

## 四、系統設計

### 4.1 菜單品項：從裝飾變成真的商品

`CafeMenuItem`（`cafe.ts:831`）已有 `id / name / price / track / level / audience`，
研發（CAFE-16～18）已經會解鎖新品項。**只需要補兩個欄位**：

```ts
interface CafeMenuItem {
  // ...既有欄位不動
  recipe: Partial<Record<CafeIngredientId, number>>;  // 新：一份要用掉哪些料、各幾單位
  baseWeight: number;                                  // 新：基礎熱門度（選品權重）
}
```

### ✅ P1 實作結果：重訂後的原料單價

初版提案的配方（咖啡豆 ×1 等）在舊單價下毛利落差過大（咖啡 56% vs 烘焙 28%）。
實作時改成 **低單價 × 多單位**，用整數粒度換到「13 個品項全部落在 45～60%」：

| 原料 | 舊單價 | **新單價** | 舊常備量 | **新常備量** | 生鮮 |
|---|---|---|---|---|---|
| 咖啡豆 | $15 | **$4** | 20 | **130** | 否 |
| 牛奶 | $12 | **$3** | 15 | **24** | 是 |
| 麵粉 | $8 | **$3** | 10 | **52** | 否 |
| 奶油 | $18 | **$10** | 8 | **24** | 是 |
| 貓罐頭 | $25 | **$6** | 8 | **56** | 否 |
| 寵物鮮食 | $20 | **$5** | 6 | **24** | 是 |

常備量取自「成熟期（產能 40、人氣滿）實測 200 天的單日尖峰消耗再留餘裕」
（尖峰：咖啡豆 124 / 牛奶 12 / 麵粉 49 / 奶油 21 / 貓罐頭 51 / 寵物鮮食 21），
三種生鮮一律 ≤ 24，維持「照建議值玩 → 零缺貨、零損耗」的懶人路線（§4.3.1）。
配套把 `SPOILAGE_FREE_UNITS` 從 6 調到 15 —— 週轉量變大了，免損耗額度得跟著等比放大，
語意仍是「一天用得完的量不會壞」。

### 4.2 熱門度與顧客選品（零 RNG）

每位顧客用**決定性雜湊**選一項商品，權重 =

```
weight(item) = item.baseWeight
             × 客群修正(guest.intent / audience)
             × 天氣修正      // 冷天熱飲 ↑、熱天冷萃 ↑
             × 時段修正      // 早上咖啡 ↑、下午烘焙 ↑
```

雜湊取自 `顧客 id | 遊戲日 | 小時`，抄 `cafeGuests.ts` 既有的 `cafeGuestHash` 作法，
**不新增任何 `Math.random()`**（多一次亂數就會位移整個模擬序列）。

**玩家從哪知道熱門度？** ✅ **P3 已實作**：咖啡廳面板的「**銷售排行**」區塊
（`cafeSalesRanking()`）列出過去 7 個遊戲日各品項的賣出杯數與缺貨次數，由高到低。
這就是需求 1「視顧客購買的產品熱門度做補貨」的資訊來源 ——
**玩家不是被告知權重，而是從銷售紀錄自己讀出來**，這才是經營感。
缺貨次數用紅色徽章單獨標出（那是玩家正在流掉的錢），下方再補一行本週撲空總人次。

### 4.3 庫存、補貨與缺貨

**補貨時機從「日結後」移到「開店前」**（每日 10:00 前一刻）：

1. 依常備量計算缺口 → **立刻扣款進貨**（錢不夠就只補得起的部分）
2. 開店，帶著這批庫存做一整天生意
3. 20:00 關店 → 扣固定開銷 → 易腐品損耗結算

這個順序讓玩家**先付錢、後賺錢**，是「經營」與「領被動收入」的分野。

**缺貨處理（需求 1 的核心）**：

| 情況 | 結果 |
|---|---|
| 配方所需原料齊全 | 扣料、`money += item.price`、聲譽 **+**、日誌「有人點了拿鐵」 |
| 缺任一項原料 | **$0 收入**、聲譽 **−**、顧客立刻離場、日誌「有人想點拿鐵，牛奶沒了」 |
| 連續缺同一品項 | 該品項的 `baseWeight` 短期下修（客人不再期待）＋額外聲譽懲罰 |

第三條是刻意的：**放著不管會愈來愈糟**，這是「經營壓力」的來源。

#### 4.3.1 懶人路線必須維持可行（拍板 Q3）

使用者要求保留現在「設一次常備量就能放著」的路線，**作為低效但可行的選項**。
設計上這靠三件事保證：

1. **常備量沿用既有機制**（`state.cafe.standingOrders`），不改成「每天手動下單」。
   設一次就會一直照那份清單補貨
2. **`suggestedStandingOrders()` 要跟著菜單走** ✅ **P3 已實作**：面板的
   「**依上週銷量建議**」按鈕（`suggestStandingOrdersFromSales()`）一鍵把常備量草稿設成
   `ceil(過去 7 個遊戲日的單日尖峰需求 × 1.15)`。三個細節：
   - **尖峰而非平均**（週末客流是平日的 1.39 倍，用平均會週週缺貨）
   - **把 `missed` 一起算進需求**（依「實際賣出」補貨會讓缺貨自我實現）
   - **菜單上的原料有「至少兩份」的底線**，剛研發完的新品不會被建議成 0
   沒有可用歷史（剛開張／舊存檔沒有 `sales`）時整份 fallback 回內建建議值，
   **永遠不會算出全 0 或 NaN**
3. **偷懶的代價是「賺得少」，不是「會倒」**：
   - 均勻備貨 → 熱門品偶爾缺、冷門品偶爾爛掉 ⇒ 毛利被兩頭吃掉
   - 估計落在**勤勞玩家的 60～70% 淨利**，仍為正值
   - 但**不足以支撐擴張**（雇人、升招牌都要現金）⇒ 想長成主業就得開始盯

⇒ 懶人玩得下去，但停在「開張期～成長期」；想走到名店期必須真的經營。
這與 §4.7 的成長曲線是同一件事的兩面。

### 4.4 開店 / 關店與一日節奏

| 遊戲時間 | 事件 | 畫面 |
|---|---|---|
| 09:00 | 進貨扣款 ✅ P3 | `cafeRestockPass()`；一天只扣一次（`sales[].restocked` 旗標） |
| **10:00** | **開店** | 招牌亮起、門打開、一樓地板恢復正常亮度 |
| 10:00–20:00 | 每小時 `ceil(當日客流 / 11)` 位顧客進場 | 逐位走進來點餐（見 §4.5） |
| **20:00** | **關店** | 顧客清場、門關、招牌熄、一樓轉暗 |
| 20:00 | 日結（實作掛在午夜換日） | 扣固定開銷 $370、**對打烊後剩餘庫存**算易腐損耗、寫 history、推日誌 |

非營業時段一樓是暗的、空的 —— **玩家一眼分得出「營業中」和「打烊」**，這本身就是需求 2。

### 4.5 看得見的消費（需求 2 的核心）

`GuestAgent` 的 phase 從 `entering → seated → leaving → departed`
擴充成：

```
entering  → ordering → (成功) served → seated → leaving → departed
                     → (缺貨) refused →                   leaving → departed
```

| phase | 畫面演出 |
|---|---|
| `entering` | 從店門走向**吧台**（固定位置） |
| `ordering` | 站在吧台前，頭上泡泡顯示**他要點的商品圖示**（不再是抽象的意圖符號） |
| `served` | **`+$34` 綠色浮字**從頭上升起、金錢數字跳動 |
| `refused` | **紅色 ❌ 泡泡**、聲譽數字閃一下紅色 |
| `seated` | 走到**固定座位**坐下（真的坐在椅子上，不是站空地板） |
| `leaving` | 起身走向店門 |

**意圖泡泡一併重做**（解決使用者「不知道標誌什麼意思」）：
- 點餐時顯示**商品圖示 + 價格**，不是抽象符號
- 「想認養寵物」「想租房」兩種可互動意圖，改成**帶文字標籤的醒目提示**，
  並在咖啡廳面板同步列出（現在只有面板有，畫面上的符號沒人看得懂）

### 4.6 座位：不鎖，但座位本身就是容量（拍板 Q4）

現況的衝突：顧客有 6 格 `CAFE_GUEST_PREFERRED_SEATS`，而開張贈品**刻意避開它們** ⇒
顧客站在空地板上。

**廢除 `CAFE_GUEST_PREFERRED_SEATS` 這張硬編座位表**，改成
**「顧客坐在玩家實際擺的椅子上」** —— 座位不是寫死的座標，而是查 `placements`：

```
內用席次 = 一樓四區裡 `seat` 欄位不為空的家具數量
（`seat` 欄位是 2026-08-03 CAFE-20 renderer 那批已經加好的，直接沿用）
```

顧客動線：**店門 → 吧台（固定 (3,38)）→ 任一空席 → 店門**

這個設計同時解決四件事，而且**不需要任何 UI 鎖定邏輯**（拍板要求「以好做為主」）：

| | |
|---|---|
| 看得到入座 | 顧客坐在真的椅子上，不再站空地板 |
| 可以拆 | 拆了不會壞，只是**席次變少** |
| 拆掉有代價 | 席次不足 → 後到的顧客**只能外帶** |
| 家具有意義 | 買椅子 = 買容量，和既有的氛圍加成（`cozy + style` → 客流）疊成兩條回饋 |

**外帶的代價**（這是「拆掉有後果」的具體化）：
- 外帶客**只點飲料，不點烘焙/寵物餐** ⇒ 客單價明顯較低
- 外帶客**不貢獻氛圍評價**，聲譽只給一半
- 全店零席次 = 純外帶店，能活但收入明顯較差，且畫面上永遠看不到人坐著

⇒ 玩家會自己發現「多擺幾張椅子比較賺」，不需要我們鎖住任何東西。

### 4.7 成長曲線：從副業長成主業（拍板 Q1）

**這一節推翻了初版的「副業」定位。** 使用者要求咖啡廳「可以慢慢成長取代收租」，
所以天花板必須真的超過租金。

#### 對照基準：租金收入

| 項目 | 數字 |

產能上限 40（`CAFE_BASE_CAPACITY 26 + CAFE_CAPACITY_PER_MACHINE 14`）
× 客單價硬上限 $38（`CAFE_MAX_AVG_TICKET`）= 日營收上限 $1,520
⇒ 扣成本後淨利上限僅約 **$390/日，只有淨租金的 36%**。

- **② 缺貨沒有設計值那麼痛**。設計表假設「照常備量付了 −$468 卻還是缺貨」，

  P1 沒有動這個定調。⇒ **「備太多反而虧」目前只成立在「賺得比較少」這個層次**。

⇒ 賺錢的唯一路徑仍然是**盯著銷售排行補貨、並且在對的時機才擴張**，
但「虧錢的五條管道」裡的第 3 條（易腐損耗）與第 4 條（缺貨複利）力道都比設計預期弱。
要不要加碼是使用者的決定，**P1 刻意不擅自調**。

#### ✅ P3 實測值（進貨移到開店前 + 損耗調校後，同一支腳本、同樣 112 個遊戲日）

第二件事之所以能調得動，是因為第一件事改變了損耗的對象：
日結時看到的不再是「剛補滿的常備量」，而是**打烊後真正沒用完的庫存**。

（以上為「靜態」模式：人氣固定 100 讓各情境客流可比。解除固定後 ② 是 **−$18**、⑤ 是 **−$158**，
人氣都掉到 0 —— 那是 §4.8 的缺貨複利在作用。）

**三個結論：**

1. **③「備太多反而虧」成立了**：+$59 → **−$35**。損耗從 −$36 拉到 −$135，
   而且它現在是**穩態成本**（每天壞掉多少，隔天早上就得買回多少）。
   離設計值 −$114 還有距離，但方向與量級都對了 —— 這條虧損管道從「賺得少」變成「真的賠」。
2. **②「只砍一種原料」仍然接近損益兩平，而且這是結構性的，不是參數問題。**
   常備訂單的語意是「補到水位」而不是「每天固定買一批」：少備料 ⇒ 少付錢。
   ② 少賣了 $180 的東西，但同時也少付了 $83 的料錢，剩下的差額大致等於毛利。
   **要讓「缺貨」真的痛，缺的必須是「錢已經花下去了、卻花錯地方」** —— 那就是 ⑤。
3. **⑤ 才是設計表 ②「缺貨 20% ⇒ −$89」真正想描述的形狀**，實測 **−$132**（自然模式 −$158）。
   玩家照樣付了一大筆進貨錢，卻做不出客人要的東西，兩頭一起被吃掉。
   ⇒ 這正是「盯著**銷售排行**補貨」有價值的原因：排行告訴你錢該花在哪一項。

**沒有為了對上設計值硬調參數**：損耗的兩顆旋鈕是由一條不等式夾出來的
（「懶人路線必須零損耗」×「多備 50% 必須虧錢」），推導完整寫在
`src/sim/cafe.ts` 的 `SPOILAGE_FREE_UNITS` 註解裡。

**懶人路線仍然可行（§4.3.1 沒有被打死）**：`CAFE_INGREDIENTS` 的建議常備量三種生鮮都是 24，
而收斂上界 `23 + ceil(1/0.9) − 1 = 24`。進貨只會把庫存補「到」常備量、消耗只會讓它變少
⇒ **夜間剩餘永遠 ≤ 24 ⇒ 損耗恆為 0**。這是數學保證，不是實測巧合
（`scripts/cafe-p3-economy-test.ts` 有直接斷言）。

或降低氛圍加成上限），**P4a 刻意不擅自決定**。

#### 不倒店（拍板 Q2）

刻意**不加**倒閉/強制歇業機制。資金為負時：
- 進貨只補得起買得起的部分（既有 `restockPlan` 已經這樣做）
- 缺貨 → 聲譽掉 → 客流掉，自然縮回小店規模
- 玩家隨時可以資遣員工止血

⇒ 懲罰是「**縮水**」而不是「**歸零**」，符合本作既有的「有代價但不是失敗狀態」基調。

### 4.9 員工與吧台：產能必須看得見（2026-08-04 使用者追問後補）

使用者問：「員工要真的有面板嗎？畫面上看得到他在做什麼嗎？會看到他幫顧客結帳嗎？
結帳在櫃檯嗎？」——**四題的答案都是「要」。**

初版 §4.7 只寫了「員工每人日薪 $260，可處理 35 杯/日」，是一個**純數字、沒有任何畫面表現**。
那等於重蹈本次要修的覆轍：看不見的數字驅動經濟，畫面上演別的事。本節補上。

#### 員工是畫面上的 agent，不是面板上的數字

新增 `src/floor/staffAgents.ts`。這是走過三次的路（`guestAgents` 229 行、
`petAgents` 220 行、`vacuumAgents` 366 行），規模預估 ~200 行。

| 忙碌 | 連續動作不停，吧台前開始**排隊** |

#### 結帳動線（固定在吧台）

```
店門 → 吧台前排隊 → 員工結帳(+$34 浮字) → 拿了飲料 → 走到空席坐下 → 離開
                  └─ 缺貨 → ❌ → 直接離開
                  └─ 無空席 → 外帶，結完帳直接離開
```

吧台位置固定 `(3,38)`（開張贈品的吧台就在這裡）。

#### 🔴 排隊 = 產能不足的視覺信號（本節最重要的一條）

**這是整個員工系統存在的理由。**

```
客流成長 → 員工處理不完 → 吧台前排隊變長 → 你看到了 → 雇人
                        └─ 排太久的顧客會放棄離開（$0 + 聲譽 −1）
```

玩家**不需要讀任何數字**就知道該擴張了 —— 看到排隊就懂。
這比面板上的「產能 35/48」好一百倍，也是「經營感」最直接的來源。

反過來，**淡季時看到員工站著發呆**，就是該考慮資遣的信號 ——
過度擴張的懲罰同樣是看得見的。

| 項目 | 結果 |
|---|---|

**為什麼判定放在模擬層而不是渲染層**（三個理由，寫在 `cafeHourlyPass()` 的註解裡）：
① $0 必須是「從沒收過」而不是「收了再退」，否則收支頁會出現玩家沒做過的交易；
② 渲染層走現實秒數，玩家沒開 1F 頁面就不會演，懲罰掛在那裡會讓「有沒有在看」改變帳本，
P1／P3 的離線一致性當場破功；③ 零 RNG（純累積差分）。

**為什麼要有 8 人的容忍線**：`base > capacity` 是一間經營良好的店的**常態**
（客流公式的 `min` 就是為此存在），天天罰它等於把 §4.7 整條成長曲線打掉，也會讓稀疏敘事
天天推同一則。有隊伍不等於有人走掉，**隊伍站不下才有人走掉** —— 8 取自
`placements.CAFE_QUEUE_MAX_DEPTH = 14` 的一半多一點。

| 招牌 Lv4・員工 1 位 | 26 | 91 | **13** | $3,094 |

⇒ 唯一會踩到的形狀是「**招牌一直升、店卻沒跟著擴張**」；雇第二位店員就同時
消滅隊伍、營收翻倍 —— 反制手段清楚，而且正是 §4.9 想要的成長迴圈。
這條也順手把下方張力 ② 補起來了：客流雖然仍被產能夾住，但「被夾掉的人」

#### ⚠️ P4b 實作後發現的兩條張力（未擅自處理）

1. **同時能結帳的人數被吧台寬度夾住**。點餐位由吧台前那一排可走格算出來，
   贈品的 2 格吧台 ⇒ 4 個位子。雇到第 5 位以上的員工不會再增加同時服務人數
   （他仍然站在吧台後、仍然算產能與薪資）。要突破得讓玩家能擺更寬／第二座吧台。
2. **客流本來就被產能夾住**（`cafeCrowd()` 的 `min(base, capacity)`），所以
   「人手不足 ⇒ 客流暴增到排爆」不會發生；隊伍長度大致是
   `每小時到客 − 同時服務人數`。**在席次是瓶頸時**（產能固定）雇人確實會讓隊伍變短；
   在員工是瓶頸時，雇人同時抬高客流，隊伍不會消失而是換成更多營收。
   兩者都合理，但與初稿「排隊長度 = 缺人程度」的直覺不完全相同。

### 4.10 地板分區產生機能差異（A 批，2026-08-16 實作）

一樓有四個區域（`cafe_floor` / `cafe_counter` / `cafe_pet` / `cafe_back`），
但在本批之前它們只是**底色不同的地板**：家具擺哪裡都只算同一份氛圍加成
（`cafeAmbiancePoints()` 的 `cozy + style`），玩家沒有任何理由把冷藏櫃放進後場。
本批給四個區域各自的機能，並且只用一條規則：

> **家具擺在對的區才有機能效果；擺錯區只剩氛圍（`cozy + style`）。**

**擺錯區不倒扣、不是失敗狀態** —— 氛圍照算，只是少拿一份機能。
`cafeAmbiancePoints()` 因此**一行未改**（改了客流乘數就會漂移）；
機能一律走 `placements.ts` 尾段新增的、**區域受限**的查詢函式。

| 區域 | 查詢函式 | 機能 |
|---|---|---|
| `cafe_back` 後場 | `cafeBackStoragePoints()` | 庫存容量上限 = `min(4000, 360 + 點數 × 40)` |
| `cafe_pet` 寵物區 | `cafePetComfortPoints()` | 寵物停留更久 + 認養詢問更容易出現 |
| `cafe_counter` 吧台區 | `cafeCounterSpan()` / `cafeCounterTechPoints()` | 同時服務人數 = `1 + 吧台寬度 + floor(tech / 3)` |

#### 三條機能的推導

- **後場選「容量」而不是「降損耗」**。降損耗會撞上既有投資項「大型冷藏」，
  而且 `SPOILAGE_FREE_UNITS = 23` / `SPOILAGE_RATE = 0.9` 是不等式 `(24 − F) × R < 1`
  的唯一解 —— 任何額外的免損耗來源都會把 §4.7 的「備太多反而虧」推回正值。
  底量 360 高於建議常備量總和 310 ⇒ **開張期玩家永遠碰不到上限**，
  補貨行為與本批之前逐字相同；名店期常備量約 900，需要「貨架 ×2 + 木箱 ×1」（$13,600）。
- **寵物區兌現了兩句一直沒接線的投資項說明**：貓跳台與軟墊的「寵物停留更久、
  認養詢問更容易出現」、店面招牌的「租屋詢問更容易出現」。`intent` 不參與結帳
  ⇒ **營收零影響**，改變的只有面板上會出現哪一種詢問卡。
  判準用 `category === "ambiance"` 而不是白名單：桌椅是 `seating`，
  玩家不能把桌椅塞進寵物區刷分。
- **吧台的「+1」是刻意的**：吧台後方的收銀／出餐口一定存在，所以「拆光吧台」
  退化成 1 個服務位而不是 0（同 `CAFE_TAKEAWAY_CAPACITY` 的哲學）。
  tech 這一項兌現了濃縮咖啡機的 `tech 3`；冷藏櫃的 `tech 2` 擺在後場不生效 ——
  **那正是分區規則本身**。必須區域受限，否則玩家可以在主廳拉一條 14 格的吧台。

#### 這一批解掉了 §4.9 的張力 ①

上面「P4b 實作後發現的兩條張力」第 1 條（同時能結帳的人數被吧台寬度夾住、
雇第 5 位以上的員工不會再增加同時服務人數）在本批得到正式答案：
**服務位就是產能公式的第三條腿**，`cafeCapability()` 用
`min(staffCount, stations)` 算出真的做得出杯子的人數，面板用 `idleStaff`
明說「有 N 位沒有吧台位置，加寬吧台才能讓他們上工」。
`cafeStaffSpots()` / `cafeCounterSpots()` / `cafeQueueTiles()` 的 lane 展開序
改讀**整個連通塊**，所以第二座吧台一接上去，員工站位與隊伍就自動變寬，
沒有第二套幾何。

⚠️ **這是唯一會咬既有存檔的改動**（使用者已核可）：雇 4 人以上、吧台仍是贈品那座的
存檔，產能 `4 × 26 = 104 → 3 × 26 = 78`。收斂性有既有論證背書，不會死亡螺旋，
而且面板會直接告訴玩家該做什麼。

#### 刻意不接：家具的 `tier` 屬性

咖啡廳的 13 件家具**每件功能唯一**，沒有「同功能不同 tier」的組
（不像三樓的沙發/電視/浴缸/書桌各有 budget/standard/premium 三檔）。
把 `tier` 接進咖啡廳的機能只會變成**雙重計價** —— 同一件家具的價格已經
反映在它的屬性點數上，再按 tier 乘一次沒有任何設計意義。
**本結論不留待辦**，日後不必再評估一次。

### 4.8 聲譽（`popularity`）重新定義

現況：`nextCafePopularity(current, { shortages, underfunded })`，換日時 +2 / −4 / −1。
改成**逐位顧客即時累積**：

| 事件 | Δ |
|---|---|
| 成功服務一位顧客 | **+0.15** |
| 缺貨導致顧客離開 | **−2.0** |
| 座位滿導致外帶 | 0（不罰，這是好事） |

夾在 0～100，仍然只影響客流 ±25%（`CAFE_POPULARITY_SWING = 0.25` 不動）。
這樣「一天服務 26 人（+3.9）」大致抵銷「兩次缺貨（−4）」—— **偶爾缺貨可以接受，
持續缺貨會崩**，符合設計檢討「有代價但不是失敗狀態」的既有基調。

## 五、技術約束（實作時不可違反）

1. 🔴 **零 RNG** — 顧客到店、選品、座位分配全部用決定性雜湊。多一次 `Math.random()`
   就會位移整個模擬序列、讓 balance 快照全盤漂移
2. 🔴 **`cafe.open` 閘門保留** — `cafeDailyPass` / 新的 `cafeHourlyPass` 第一行都必須是
   `if (!state.cafe.open) return;`。這是快照零漂移的天然保證
3. 🔴 **`cafe.ts` 的純函式界線** — 該檔不 import `state`、不呼叫 `addMoney`、不推日誌。
   算式放 `cafe.ts`、副作用放 `tick.ts`。`cafe-supply-test.ts` 有硬斷言掃描原始碼守這條線
4. **離線一致性** — 每小時 pass 必須讓「線上跑 11 小時」與「離線回來補 11 小時」結果完全相同
5. **存檔升級** — 新增 `state.cafe.sales`（銷售紀錄）、品項庫存語意變更 ⇒ 需要
   `SAVE_VERSION 8 → 9` 與對應 migration。舊檔的 `standingOrders` / `stock` 要能平順轉換

## 八、這份設計刻意不做的事

- **不做即時逐秒模擬**。遊戲是「異步掛機觀察型」，每小時結算一次已經足夠，
  而且與既有的 `hourlyTick` / `syncToNow` 架構天然相容
- **不動三樓租客系統**。咖啡廳與租客的交集只有 CAFE-19（租屋詢問）、CAFE-20（下樓喝咖啡）
  與 CAFE-09（認養），這三條介面保持不變
- **不改五項永久投資的既有數值**。招牌/咖啡機/戶外座位/冷藏/貓跳台的效果沿用，
  只是它們現在作用在一個真的會動的系統上
