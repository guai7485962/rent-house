## 1. AI 生成文本

### 現況
- `worker/index.ts` 的 `/api/narrate` 一次呼叫 Gemini,回 `{diary, newMemory, event}`。
- context 由 `store.buildNarrateCtx()` 組:當天日誌、性格、記憶、關係、鄰居、房東抉擇。
- 每「遊戲日」換日、且為 live 時觸發(每租客一次);離線/超額 fallback 模板(`narrate.ts` + `content/observationLines.ts`)。

### 問題
1. **每天各自為政**:AI 只看「當天」片段 + 靜態記憶,缺「昨天寫了什麼」的連續感 → 容易同質、劇情不連貫。
2. **context 沒有壓縮/摘要**:租客住越久,memoryTags/關係越多,prompt 越長、成本越高、重點越糊。
3. **額度脆弱**:Gemini 免費層每分鐘/每日上限低,4 租客同時換日 = 瞬間 4 次;快轉跨多日會爆。
4. **無快取/去重**:相似情境重複呼叫。

### 優化設計
- **加「連續性摘要」**:每位租客維護一段滾動 `narrativeSummary`(≤200 字),每次 AI 回傳時**順便更新它**(prompt 要求輸出 `summaryUpdate`),下次把它餵進去。→ 用一個短摘要取代「塞一堆歷史」,又保連貫。
  ```ts
  interface NarrateResult { diary; newMemory; event; summaryUpdate?: string }  // worker 回傳新增
  TenantRuntime.narrativeSummary: string                                      // 取代/補強 tenant.recentSummary
  ```
- **context 預算化**:`buildNarrateCtx` 只帶「最近 N 筆重點日誌 + 最新摘要 + 最多 K 個最相關記憶 + 進行中關係」,其餘丟摘要。
- **佇列/節流**:換日時把多位租客的 narrate 請求**排隊**(間隔 ≥ RPM 限制),而非並發;可在 `store` 加一個簡單的 `narrationQueue`。
- **供應商抽象**:worker 內把「呼叫哪個模型」抽成 `providers/{gemini,claude}.ts`,方便日後換 2.0/2.5 或加重試/退避(429 自動退避 N 秒)。
- **可選:輕量快取**:對「狀態雷同、無新記憶」的日子直接走模板,省呼叫。
- 優先序:連續性摘要 **高**;節流/退避 **高**(額度痛點);context 預算化 **中**;快取 **低**。

## 2. AI 影響劇情(讓 AI 更深、更安全地影響世界)

### 現況
- AI 事件可影響單一租客,或**牽涉第二位鄰居**(`other`/`rel`,嚴格夾值、取向把關);記憶標籤已能**改行為**(`memoryEffects.ts`)。

### 問題
1. **沒有「長期劇情弧」**:事件是一次性的,缺「連載」——第 3 天埋的伏筆第 10 天回收。
2. **記憶會無限累積又同權**:8 個上限、先進先出,沒有「淡出/強化/演化」(失戀該慢慢好起來)。
3. **事件彼此獨立**:缺因果連鎖(A 事件的選擇 → 解鎖 B 事件)。

### 優化設計
- **記憶生命週期**:給記憶加 `intensity`(0~1)與 `decayPerDay`,每日衰減;`memoryDrift` 乘上 intensity;衰到 0 自動移除。讓「失戀」隨時間淡化、痊癒。
  ```ts
  interface MemoryTag { …; intensity: number; decayPerDay: number }
  ```
- ~~**劇情弧 (Arc)**~~ ✅ 2026-07-11(`sim/arcs.ts`:每位租客 0~1 條,AI 每日推進/收束,sanitizeArcUpdate 消毒):每位租客可有 0~1 條進行中的 arc(`ThreadState`),AI 每日推進一步;arc 提供「連載」骨架。
  ```ts
  interface StoryArc { id; theme: string; stage: number; maxStage: number; summary: string }
  TenantRuntime.arc?: StoryArc
  ```
  prompt 告知目前 arc 與 stage,要求 AI「推進或收束」。
- ~~**事件連鎖**~~ ✅ 2026-07-11(事件選項 effect.flag → rt.flags 去重 cap 12 → 每日餵回 AI 回收;rollEvent 依 flag 解鎖規則事件留待事件資料化時接上):AI 事件的選擇可留一個 `flag`(記入租客),之後 `rollEvent`/AI 依 flag 解鎖後續事件。
- **關係網 → 群體事件**:目前社交是兩兩;可加「三角關係/室友公約/公共衝突」等牽涉 3+ 人的事件(需擴充事件 target 為多人)。
- **安全**:所有新增影響一律延續現有原則(store 端夾值、玩家抉擇、不開放驅逐、名字要對得上 roster、忽略未知欄位)。arc/flag 也要 schema 驗證。
- 優先序:記憶生命週期 **高**(便宜、直接讓劇情更真);劇情弧 **中**;事件連鎖 **中**;群體事件 **低**。

## 4. 租客數值模型(重點)

### 現況
- `Tenant.stats = { mood, stress, hygiene, affinity }` + `TenantRuntime.satisfaction`(衍生)。
- **問題最集中的地方**:
  1. **`hygiene` 幾乎沒用**(只有記憶漂移剛接上,無日常來源/後果)。
  2. **會飽和**:mood/stress 容易黏在 0 或 100。
  3. **語意重疊**:mood 與 satisfaction、stress 與 satisfaction 部分重疊。
  4. **和經濟脫節**:租客沒有「自己的錢/財務壓力」,繳租只看 reliability+affinity+satisfaction。

### 優化設計(建議的數值軸重整)
把數值分成**三類**,語意清楚、彼此有因果:

**A. 即時情緒(短期、每小時波動)**
- `mood` 心情、`stress` 壓力、`energy`(**新增**,精力:睡覺/放鬆↑、工作/加班↓;energy 低 → 效率差、易 stress)。

**B. 狀態(中期、緩慢變化)**
- `hygiene` → 改名/擴為 `wellbeing`(身心健康:運動/衛生↑、熬夜/高壓↓),並**給它後果**(低 → 生病事件、mood 上限下降)。
- `affinity` 對房東好感(保留)。

**C. 衍生(唯讀,由上面算)**
- `satisfaction` 居住滿意(現有公式再納入 wellbeing/energy)。
- **新增 `socialFulfillment`**:由社交關係算出(有朋友/戀人↑、孤立↓)→ 影響 mood,讓社交系統回饋到數值。

**租客財務(新增,和經濟扣緊)**
```ts
Tenant.wallet: { balance: number; monthlyIncome: number }   // 租客自己的收支
```
- 租客有收入/開銷;`monthsOverdue` 真正由 wallet 決定 → 「繳不出租」變成有根據的劇情,而非隨機。

**抗飽和機制**
- 所有每小時 delta 改成**朝基準值回歸 (homeostasis)**:`stat += (baseline - stat) * k + event/memory/routine deltas`。個性決定 baseline(工作狂 stress baseline 高)。→ 自然不黏 0/100,且性格差異體現在「回到哪」。

- 優先序:抗飽和(homeostasis)**高**(治本、影響全域手感);啟用/重定義 wellbeing + 後果 **高**;energy **中**;socialFulfillment **中**;租客 wallet **中**。
- 風險:改數值軸會牽動 satisfaction/事件/社交/收租多處,需集中一次重構 + 大量回歸測試(`sim-trace`、新增 balance 快照測試)。

## 5. 整體架構 / 擴充性 / 效能 / 資料模型

### 現況與問題
1. **`store.ts` 過大**(~700+ 行,tick/作息/事件/社交/AI/收支/存檔/擺放全在一起)→ 難維護、易改壞。
2. **存檔**:單一 localStorage blob、手寫欄位、`?? 預設` 式相容;版本欄位 `v:2` 但無正式遷移層。
3. **reactive 效能**:每 rAF 重繪整個 canvas;租客多時 `Object.values(runtimes)` 反覆掃描。目前規模 OK,但要留意。
4. **內容資料驅動**:家具/文本已資料化;事件(規則式)、作息仍寫死在程式。

### 優化設計
- **拆 store 成多個 slice/模組**(仍共用一個 reactive `state`):
  - `sim/tick.ts`(hourlyTick + applyHour + 偏離)、`economy.ts`(addMoney/collectRent/upkeep/ledger)、`tenancy.ts`(moveIn/moveOut/招租/佔用/配色)、`narration.ts`(每日 AI/摘要/佇列)、`persistence.ts`(save/load/migrate)。`store.ts` 只留 `state` 定義 + 對外 re-export。
- **正式存檔遷移層**:`persistence.ts` 內 `migrate(raw): SaveV3`,一段一段版本升級;`SAVE_VERSION` 常數;壞檔安全 fallback。
- **事件與作息資料化**:把 `events.ts` 的規則式事件、`routine.ts` 的作息抽成 `data/*.json` 或 catalog 式陣列,讓「加事件/改作息 = 改資料」。
- **效能**(有需要再做):agents/canvas 只在「有變化」時重繪;`occupancy`/`runtimes` 掃描結果快取。
- **測試策略**:除了 `sim-trace`,加「**balance 快照測試**」——固定隨機種子跑 N 天,快照關鍵數值/金錢曲線,改動時 diff,避免手感悄悄跑掉。
- 優先序:store 拆分 **高**(所有後續工作的地基);存檔遷移層 **高**(改資料結構前必備);事件/作息資料化 **中**;效能 **低**;balance 快照測試 **中**。

#### 10-1a. 不稀釋的主池/次池抽籤 ✅ 2026-08-18(G 批第 1 批,`sim/interactions.ts` `pickInteraction()`)

**問題**:`runGroup()` 原本是「先按 weight 從全部候選抽一個 def,再擲該 def 的 chance」,每對消耗
**恰好 2 顆骰**。目錄一擴充,分母跟著變大 ⇒ 既有內容被稀釋(實測 `game_night` 12.5% → 3.1%)。
把新內容的 weight 調低也治不了——weight 影響的是「被抽中」而不是「總量」,壓低只是把稀釋換個地方發生。

**解法**:`InteractionDef` 加 `pool?: "core" | "extra"`(省略 = core),抽籤拆成兩階段:

1. **主池非空 ⇒ 與擴充前逐位元相同**:同一顆 weight 骰、同一個分母(只算 core)、同一個累減順序,
   再擲同一顆 `chanceRoll`,命中語意仍是 `<=`。既有 18 種的觸發率變化是 **0.000%**,不是「近似」。
2. **主池落空時不再擲骰**,而是把已經花掉的 `chanceRoll` 換算成 `u = (chanceRoll − c) / (1 − c)` 去抽次池。
   合法性:在「`chanceRoll > c`」這個條件下 `chanceRoll` 在 `[c,1)` 均勻,故 `u` 在 `[0,1)` 均勻。
   **零新 `Math.random()`** ⇒ 全域亂數序列不位移 ⇒ balance 快照零漂移。
3. 次池以「預算」累加 `(w_i/W)·c_i`,故 extra 的絕對觸發率 = `(1−P_core)·(w_i/W)·c_i`。
   調高任一 extra 只吃掉次池自己的預算,**永不反噬主池**;`P_core` 實測約 0.25~0.45。

**唯一的擲骰次數變動**:`core 空 + extra 非空` 會多擲 1 顆(原本 0 顆)。因此所有 extra def
**一律 `tier: "close"` 以上**——⚠️ 絕不可為此新增更低的 tier(如 `acquaintance`),那會讓全樓
每一組低關係配對都多擲一顆,漂移量級完全不同。備案是把該分支直接 `continue`(犧牲次池在低關係場合的曝光)。

**`gateOk(gate, A, B)`(劇情前提閘,零 RNG)**:`one_broke` / `one_unwell` / `both_adult` / `deep_couple`。
**刻意不併進 `canInteract()`**——那個函式是「安全硬規則的唯一入口」(分級/成年/私密),
gate 只是劇情前提;混進去會稀釋語意,也會逼簽章從 `Tenant` 改成 `TenantRuntime`,打壞既有測試 fixture。
gate 只會讓 def 更難觸發,不會放寬任何安全條件,故 `forceInteraction()`(AI 提議)也照樣過閘。

**`lend` / `needyBonus`**:兩者都零 RNG。`lend` 只在兩人的 `rt.wallet` 之間搬,**不動 `state.money`**
(房東帳與租客錢包是兩本帳);`needyBonus` 加在 `wellbeing` 較低的一方,一律夾 0~100。

**驗收**:`scripts/interaction-pool-test.ts`(46 項)。最強的一條是「同種子下含 extra 與濾掉 extra
選出的主池序列逐位元相同(含物件 identity、命中次數、擲骰總數)」;另有擲骰次數三情境、預算公式
蒙地卡羅、`u` 的 10-bucket 均勻性、gate 邊界、`lend` 守恆。`balance-test` 零漂移。

**三個一定要記住的坑**:

1. **文案不可以寫單向句。** `performInteraction()` 對兩人**推同一句**、只把 `{o}` 換成對方名字,
   所以「我借錢給{o}」在對方的日誌上語意會整個反過來。一律寫成「和{o}…」「{o}和自己…」的

2. **`requiresFurniture` 對 `venue` 無效。** `furnitureSetOf()` 只查 `p.room === roomId`,

   `standAt` 也用不了,那需要長度 ≥2 的家具)。`interaction-pool-test.ts` 加了掃描把關。
3. **負向互動不得餵養冷戰/打架。** `bathroom_rush` 是目錄裡唯一的負向互動,rel **只扣 1**,

| 情境 | 壓力基準 | 口角 | 冷戰 | 打架 | 單人 stress 最高 | 配對「較低者」最高 |
|---|---|---|---|---|---|---|

**瓶頸 100% 在壓力門檻,而且是結構性的**:

1. `applyHour` 的活動增量長期為負(睡覺 −5/h、洗澡 −4、打電動 −3、看電視 −1),

  每換一次 rel/tension 從 0 重來——這是「打架難見」的第二個獨立成因,和門檻無關。
- **突發事件系統在健康局裡完全靜默**:60 天 4 位租客,`rollEvent()` 一次都沒有觸發

原因:所有懲罰都是**脈衝**,而四條數值全部有回歸,脈衝一定會被抹平。

| 懲罰 | 實作 | 回歸 | 對平衡點的**實際**位移 |
|---|---|---|---|
| 壞著沒修 `satisfaction −7/日` | `maintenance.ts` | 20%/h | **−1.45** |
| 壞著沒修 `mood −4/日` | `maintenance.ts` | 6%/h | −2.15 → 經權重 ×0.25 = **−0.54** |
| 壞著沒修 → `affinity` | **不存在** | — | **0** |
| 及時修繕 `affinity +5` | `maintenance.ts` | **不回歸** | **+5(永久)** |

熱水器壞六天不修,滿意度長期只掉約 2 點、好感 0 點;修好一次卻永久 +5。
**虧待免費、照顧單向加分** —— 這才是根,調門檻一輩子都調不好。

### 2. 機制:`neglectPoints(rt)` + 四條掛載點

`src/sim/maintenance.ts` 的 `neglectPoints(rt)` 回 0~6:故障拖延天數(封頂 6)
+「答應改善房間」空頭支票旗標 +2,再夾到 6。不新增存檔欄位(`sinceMs` 與 `rt.flags`
都已入檔,`SAVE_VERSION` 不動)、無虧待時恆為 0、`repairBreakdown()` 後立刻回 0,
而且每一分都來自玩家**收到過明確通知**或**親手按過按鈕**——刻意排除「多久沒送宵夜」
「多久沒互動」這種「什麼都沒做也會發生」的來源。

🔴 **四條數值的槓桿倍率完全不同,絕不可共用一組常數**(這是本批最容易做錯的地方):

| 數值 | 回歸 | 掛在哪 | 位移倍率 | 係數 |
|---|---|---|---|---|
| `stress` | 6%/h | `baselines()` 末段 | **×1**(掛每小時增量會變 ×16.7 直接爆表) | +2 / 點 |
| `wellbeing` | 1%/h | 每小時增量 | **×100**(掛 `wbAnchor` 只有 ×1,且幅度只有 ±4) | −0.03 / 點·h |
| `satisfaction` | 20%/h | `target` | ×1(掛脈衝只剩 ×0.21) | −3 / 點 |
| `affinity` | **無回歸** | **每日一次** | 永久累積(掛每小時 = ×24,兩天歸零) | −0.25 / 點·日 |

另外把 `applyStat` 的 `stress >= 80 → wellbeing −0.4` **階梯**改成 `stress > 60` 起的
**斜坡** `−0.02 × (stress − 60)`:實測壓力平衡點落在 `baselines()` 基準**下方約 20 點**,
那道階梯幾乎踩不到 ⇒ `sick` 的 `wellbeing ≤ 28` 永遠走不到。`stress = 80` 那一點
**恰好仍是 −0.4**(向後相容錨點),`stats-model-test.ts` 把 80/79/60 三個點釘死。

門檻只動一則:`breakdown` 的 `stress >= 90` → `>= 72` 且加第二條 `neglect >= 1`。
`sick` / `dissatisfied` / `grievance` 的門檻**一個數字都沒動**——那三則原封不動地活了過來,
正是「只修管道、不修門檻」的證據。事件冷卻 2 → **4** 遊戲日(見下面第 4 點)。

### 3. 🔴 可達性證明裡的循環相依(設計原案的致命傷)

原設計把上限訂成「故障拖延最多 4 分 + 旗標 2 分」,而三則事件的可達性**全部用滿分 6 推導**。
但那個旗標的唯一來源是玩家在 `dissatisfied` 選 `promise`,而 `dissatisfied` 又要虧待度
接近滿分才觸發:

```
n=6 需要旗標 → 旗標需要 dissatisfied 觸發 → dissatisfied 需要 n=6
```

用單靠故障能拿到的 n=4 重算,`breakdown` 只到峰值 71.5、差門檻 0.5 點 —— 正是使用者
原本抱怨的「剛好差一點永遠碰不到」換個地方再犯一次。**現行規則:主幹來源(故障拖延)
自己就要能到頂,由玩家選擇而來的部分只能當加速器**;`scripts/neglect-test.ts` 有一條
專門的回歸鎖釘住它。

### 5. 已知取捨:`dissatisfied` 的頻率與「AI 事件機會日」互斥

規則事件與 AI 事件**共用** `lastEventDay`(`tick.ts` vs `narration.ts:305`),所以:

- 每位租客每 4 遊戲日最多一則規則事件 ⇒ 上限 7.5 / 租客·30 日
- 每觸發一則規則事件,就吃掉約 **3 個** AI 事件機會日
- 指標 4 要求機會日降幅 < 25% ⇒ 規則事件總數**上限約 2.8 / 租客·30 日**

而規格指標 1 的四個下界加起來已經是 1.8+(續集還要另計),上界 6 **在結構上不可能達成**。
實測兩個端點:

| `NEGLECT_SATISFACTION_PER_POINT` | `dissatisfied` | `grievance` | AI 機會日(absent/extreme) |
|---|---|---|---|
| **3(現行)** | 0.264 ⚠️ | 0.352 ✅ | 0.728(−21.3%)✅ |
| 4.5 | 1.280 ✅ | 0.064 ❌ | 0.603(−34.8%)❌ |

取 3 的理由:**四則根事件的頻率彼此相當**(0.26 / 0.53 / 0.26 / 0.35),沒有一則吃掉整個事件槽;
取 4.5 則是 `dissatisfied` + `promise_due` 形成自我餵食的迴圈,把 `grievance` 餓回幾乎死碼,
還打破指標 4。使用者最近才回報「AI 事件太少」,所以**優先保 AI 機會日**。
要提高 `dissatisfied` 的話,真正該解的是「規則事件與 AI 事件共用一個冷卻槽」,不是調係數。

### 6. 量測腳本本身的兩個坑(給下一位)

1. **不能用 `conflict-freq-sim.ts` 內建的模範房東量本批**:它每小時全修 ⇒ 虧待度恆為 0;
   又對 `satisfaction < 45` 送宵夜(`affinity +4/日`)⇒ 完全蓋過虧待造成的每日流失。
   所以本腳本跑 `caring` / `lax` / `absent` 三組。
2. **`absent` 的抉擇不能盲取最後一項**:`grievance` 最後一項是 `evict`(趕走租客、截斷量測)、
   `rent_plea` 最後一項是 `forgive`(`affinity +14`,與放牛吃草相反)、`dissatisfied` 最後一項是
   `ignore`(不留旗標 ⇒ `promise_due` 永遠量不到)。三者都在 `CHOICE_OVERRIDE` 白名單裡。
   另外 `lax` 的「拖 N 日才修」必須 **N > 虧待度上限**,否則虧待度封不了頂、`sick` 幾乎不觸發,
   整條 `sick → 讓他自己休養 → 修好 → 康復 → sick_aftermath` 的鏈就量不到。
